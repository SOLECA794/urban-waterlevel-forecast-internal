## 2. 模型质量

### 2.1 离线指标（3 折分块交叉验证，n_train=168470，训练 88.56s）

| 线性外推 | 1h | 0.0233 | −0.242 | **−0.242** | 49.3% | 0.0325 |
| 线性外推 | 3h | 0.0631 | −1.704 | **−0.645** | — | — |

| 线性外推 | 12h | 0.2413 | −17.234 | **−3.270** | 26.5% | 0.1254 |
| **融合（上线）** | 1h | **0.0093** | **0.754** | **+0.503** | 92.4% | 0.0050 |
| **融合（上线）** | 3h | **0.0184** | **0.770** | **+0.520** | 96.7% | 0.0074 |
| **融合（上线）** | 6h | **0.0249** | **0.781** | **+0.532** | 95.8% | 0.0097 |
| **融合（上线）** | 12h | **0.0341** | **0.636** | **+0.396** | 94.7% | 0.0134 |

三条**能证伪**的结论：

1. **融合模型全面优于持久化基线**（四个预见期 skill 全为正，0.396~0.532）。
   如果模型只是 «水位不变» 的复读机，这一栏会是 0。
2. **线性外推比基线还差**（1h −0.242 → 12h −3.270）。
   这条是反向证据：它说明「把当前斜率一路外推」这种最朴素的预测方法真的会错到离谱
   （退水期会外推到负值），主模型的价值不是来自「预测」这个动作本身，而是来自特征。
3. **90% 区间标定合理**（PICP90 92.4%~96.7%，都落在 88~98% 的合理带里）。
   区间如果只有 50% 覆盖，说明 σ 估小了、区间是假的。

### 2.2 事件样本（预见期末积水深 ≥ 蓝色阈值，event_n=3161）

| 模型 | 1h event_skill | 3h | 6h | 12h |
|---|---|---|---|---|
| 线性外推 | +0.281 | **−0.279** | **−0.583** | −0.131 |
| 梯度提升树 | +0.700 | +0.536 | +0.491 | +0.306 |
| **融合（上线）** | **+0.700** | **+0.536** | **+0.491** | **+0.297** |

为什么要单独报这一栏：全样本指标会被大量「平静时刻」稀释掉。
平静时刻水位几乎不动，持久化基线误差接近 0，谁都能拿高分。
**只暴雨时刻的样本才是这套系统存在的理由**——在这个子集上，
线性外推在 3h/6h 直接变成负 skill，而融合模型仍保持 +0.49~+0.54。

### 2.3 在线滚动评估（这是「上线后到底准不准」的答案）

| 口径 | 数值 |
|---|---|
| 1h 已结算样本 | n=10 |
| RMSE | 0.0605 m |
| 基线 RMSE | 0.0969 m |
| **skill** | **+0.376** |

两条检查：`在线滚动评估已结算`、`在线 skill 口径可信（未被高程差虚抬）`。

**skill 必须 < 0.95** 这条阈值本身就是一处的防线。原因见 §4.2：
早期版本用「实际值的标准差」当基线分母，跨站点高程差（基准水位 3.6~16.3m）
远大于预测误差，skill 被虚抬到 **0.9826**——一个漂亮但毫无意义的数字。
现在分母改成「发布预测那一刻的实测水位」（真正的持久化基线），
数值回到 0.32~0.38，与离线 1h skill +0.503 同量级。

### 2.4 特征重要性（3h 模型，置换重要性 top）

`saturation 0.824` · `fc_3h 0.195` · `fc_excess_3h 0.134` · `rain_sum_1440m 0.057` ·
`impervious 0.057` · `fc_1h 0.053` · `headroom_red 0.048` · `fc_6h 0.030`

物理上说得通：**当前饱和度**决定还能装多少水，**未来 3 小时雨量**决定要来多少水，
**距离红色阈值还剩多少**决定后果多严重。用置换重要性而不是模型自带的 split 计数，
是因为 split 计数会把「把特征打乱后误差涨多少」这件事换成一个与分裂次数相关的
间接量，在特征相关时具有误导性。

## 3. 暴雨演练与四态闭环

### 3.1 演练流程

模拟器 60x 加速，天上什么时候下雨不由验收决定，所以有两个**演练专用**接口：

| 步骤 | 接口 | 实测返回 |
|---|---|---|
| 清零积水并停雨 | `POST /api/sim/reset-water?clear_sky=true` | `{"ok":true,"sites":10,"clear_sky":true,"dropped_pending":160}` |
| 清零后无残留预警 | `GET /api/overview` | 仍报预警的站点：**空** |
| 注入暴雨 | `POST /api/sim/storm?peak=160&dur=30` | `start_step=17877 dur=30步 peak=160mm/h 时长=150min` |
| 多站点预警触发 | 轮询 `/api/overview` | 共 9 次站点-等级首次出现，最高等级 **red** |

注入 160mm/h 的雨之后，实测 `/api/overview` 十个站点全部进入预警：
**9 红 1 橙**（水位 0.379~0.679m，综合分 0.697~0.938）。

### 3.2 四态迁移（两条路径都实测走通）

```
ACTIVE_UNACK ──人工确认──> ACTIVE_ACK ──条件消失──> CLEARED_ACK
      │
      └──────条件消失──────> CLEARED_UNACK
```

| 检查项 | 实测 |
|---|---|
| 初始态为 `ACTIVE_UNACK` | `id=117 S01 state=ACTIVE_UNACK` |
| 人工确认 `ACTIVE_UNACK → ACTIVE_ACK` | `id=117 state=ACTIVE_ACK` |
| **重复确认返回 409** | `HTTP 409 {"error":"已确认，无需重复确认"}` |
| 条件消失自动解除 `ACTIVE_ACK → CLEARED_ACK` | `id=117 终态=CLEARED_ACK` |
| 未确认事件落到 `CLEARED_UNACK` | **94 条**（另一条迁移路径） |

「重复确认返回 409」这条很重要：**非法迁移必须被拒绝，而不是静默成功**。
静默成功会让值班员以为自己确认了，实际上什么都没发生。

### 3.3 处置闭环（第二条状态机）

四态回答「预警还成立吗」，处置回答「我们做了什么」。两条轴分开测，因为合成
一个状态机就表达不了「雨已经停了、人还没到现场」。

| 操作 | 结果 |
|---|---|
| `POST /alerts/{id}/assign {assignee}` | 200，`assignee=排水公司 张工`，写入 `kind=dispatch` 备注 |
| `POST /alerts/{id}/disposition {dispatched}` | 200，`open → dispatched` |
| 同态重复推进 | **409** `{"error":"已经是「已派单」，无需重复操作"}` |
| 非法迁移 `dispatched → open` | **409** `{"error":"不能从「已派单」直接改为「待处置」"}` |
| `POST /alerts/{id}/notes` | 200，写入 `kind=note` |
| 处置卷宗 | 3 条备注（dispatch / status / note 三类齐全），`assignee` 与 `disposition` 已落库 |

`dispatched` 不能退回 `open` 是刻意设计的：**已经派出去的人不能假装没派过**。

## 4. 验收过程中抓到并修掉的真问题

这一节是全篇最有价值的部分。上面 53 条 PASS 不是一开始就绿的，
下面每一条都是**先红过**、定位到根因、修完之后才转绿的。

### 4.1 参数名不一致导致已解除事件永远查不到（最隐蔽）

- **现象**：验收脚本查 `/api/alerts?active_only=false&limit=50`，
  某个明明已经 `CLEARED_ACK` 的事件 **怎么都查不到**，检查项直接 FAIL。
- **根因**：Go 端 `listAlerts` 读的是 `r.URL.Query().Get("active")`，
  脚本传的是 `active_only`。取不到就走默认值 `activeOnly = true`，
  于是「只看活跃」的过滤被**静默施加**，已解除的事件被挡在外面。
  前端传的是 `active=1|0`，所以前端一直是好的——只有验收脚本踩中。
- **修法**：两种拼写都收（`active` / `active_only`，`0`/`false` 都算假）。
- **教训**：**参数名不一致引发的静默降级，比直接报错难查十倍**。
  报错至少会告诉你哪里错了；静默降级只会让结果看起来「确实没有这条数据」。

### 4.2 在线 skill 被高程差虚抬到 0.98

- **现象**：`/api/metrics` 的 `rolling` 里 skill 高达 0.9826 / 0.9403 / 0.9462 / 0.9316。
  模型不可能这么好。
- **根因**：`EvalStore.window_stats` 把 `sqrt(mean((actual - actual.mean())**2))`
  当成持久化基线的 RMSE。但 `actual` 是**绝对水位**，十个站点的基准高程差
  3.6~16.3 米，这个「标准差」算出来是几米级，而预测误差只有几厘米级。
  分母被放大两个数量级，skill 自然趋近 1。
- **修法**：给 `prediction` 表加 `origin_level` 列（发布预测那一刻的实测水位），
  基线误差改成 `origin_level - actual`，新增输出的 `baseline_rmse` 字段让口径可见。
  加列必须用 `PRAGMA table_info` 检查后 `ALTER TABLE ADD COLUMN`——
  `CREATE TABLE IF NOT EXISTS` 不会给已存在的表补字段。
- **验收防线**：检查项直接卡 `skill < 0.95`。数字太漂亮时先怀疑分母。

### 4.3 量纲混用：预测增量被当成绝对水位（误差 +7.85m）

- **现象**：S01 的预测水位撞到物理上界 `base+1.5`，预警直接判红。
  `/state` 里 `corrected=3.2292`，`reason` 写着 **「系统性偏差 +7.849m」**。
- **根因**：模型的预测目标是**水位增量 Δy**（增量更平稳、以观测为锚），
  但 `warmup_corrector` 里 `_predict()` 的返回值被直接拿去和
  `ds.level[o + hstep]`（绝对水位）比较。误差均值算出来 ≈ +7.85m，
  正好是 S01 的基准高程。
- **修法**：`yhat = ds.level[o, sites] + self._predict(X, sites, hstep)`。
  修后 err_mean 回到 −0.003~+0.003、err_abs 0.006~0.011。
- **教训**：**「水位」和「水位增量」必须是两种类型**。它们能相加（`level + delta`），
  但不是同一个量纲，混用不会报错，只会给出一个看起来合理的错误数字。
- **加固**：加了防呆闸门 `applied = clip(corr.applied, -3σ, +3σ)`——
  修正器再出问题，也不允许把曲线推出置信带。

### 4.4 仿真时钟被重启重置，一张图定格在旧时刻

- **现象**：重启后 `/api/overview` 的 `issued_at` 停在 `1792618800`（2026-10-22 05:40），
  而 `/api/health` 的 `ts` 是当前时间。页面看起来在刷新，数据其实是旧的。
- **根因**：模拟器 60x 加速，仿真时间早就跑到墙钟前面。而
  `engine/app/api.py` 的 `_loop()` 每次启动都把 `base_ts` 重置到数据集末尾
  （`ds.ts[-1]`），于是新遥测的时间戳比 Go 库里 `MAX(ts)` 还小，
  `NowTS()` 卡在旧的未来值；新预测的 `issued_at` 也小于旧快照，Go 按
  `issued_at DESC` 取到的还是旧预测。**两个都是静默错误，没有一行报错。**
- **修法**：新增 `engine/data/sim_clock.json` 记录仿真时钟；
  启动时取 `max(数据集末尾, 上次落盘的 last_ts)`，**再向 Go 问一次
  `/api/health` 的 ts 和 `/api/forecast` 的 issued_at**，谁更大用谁。
  落盘时机是 `ticks == 1 or ticks % 12 == 0`——只写 12 的倍数是不够的，
  刚启动就被停掉的进程会留不下任何时钟，下次重启又回到数据集末尾。
- **教训**：凡是「累计状态 + 重启」的组合，都要问一句**重启后从哪儿接着数**。

### 4.5 退水太慢导致四态闭环验收等不到「解除」

- **现象**：注入暴雨后等 6 分钟墙钟（= 6 小时仿真），
  预警始终保持红色，`ACTIVE_ACK → CLEARED_ACK` 检查超时 FAIL。
- **根因**：不是四态机的问题，是**模拟器的物理特性**。
  S01 积水面积 16 ha、水深 0.7m，管网排水 26mm/h × 汇水面积 × 效率(0.65)
  ≈ 1338 m³/步，而漫溢拓宽因子 `widen = 1 + 6·(h-spill)/spill` 把有效面积
  放大到 4.43 倍，`Δh ≈ −0.0227 m/h`——从 0.70m 退到 0.45m 要 11 小时仿真。
- **修法**：**没有改物理参数**（改了就不是这个模型了），而是加演练接口
  `reset-water`，并把验收脚本改成「清零 → 注入 → 升到红 → 确认 → 再清零 → 等解除」。
  同时该接口会**作废清零前的未结算预测**（`dropped_pending`）：
  那些预测瞄准的是被抹掉的那条洪水曲线，留着结算只会把在线 skill 抬成假数字。
- **教训**：**当测试等不到结果时，先分清是系统错了还是测试设计错了**。
  这里的四态机是对的（两条迁移路径此前已单独验证过），错的是「让验收去等
  十几个小时仿真时间」这个想法。用演练控制消除等待，比放宽超时或调物理参数都诚实。

### 4.6 契约不匹配导致整页白屏

- **现象**：`/model` 整页空白，控制台 `TypeError: v.map is not a function`，
  页面 `nodes:9`、`text:""`。
- **根因**：前端类型定义与引擎 `/metrics` 实际返回不符：
  `feature_importance` 的元素字段是 `name` 不是 `feature`；
  `rolling` 是**按预见期键的对象** `{"60":{...}}` 不是数组；
  `trained_at` 是**数字 unix 秒**不是字符串；
  引擎根本没有 `n_features` / `n_samples` / `feature_names` / `importance` 字段。
- **修法**：引擎 `/metrics` 补 `n_features`，前端按真实形状重写 `MetricsBundle`。
- **定位手段**：`scripts/probe-page.mjs` —— 用 CDP 抓某路由的控制台报错与
  `/api/*` 网络状态。**没有这个工具就只能靠猜**，而 React 的渲染崩溃
  在页面上只表现为「一片空白」，什么线索都没有。

### 4.7 审计记不到操作人（中间件顺序的静默失败）

- **现象**：`/api/audit` 里每一条都是 `"username":"","role":""`。接口 200、字段齐全，
  前端也照常渲染——只是「谁干的」这一列永远空着。
- **根因**：`Audit` 中间件挂在 `Authenticate` **外层**（它要包住整个请求才能拿到
  handler 写完的 status），而 `context` 只能往下传不能往上回。`next.ServeHTTP` 返回后
  外层读到的仍是它自己那份 context，里面没有身份。
- **修法**：`Audit` 造一个 `slot := &Identity{}` 放进 context 往下传，
  `Authenticate` 校验通过后往这个指针里写。登录接口额外手动填一次——
  **登录那一刻还没有会话，`Authenticate` 不跑**，否则审计里只剩「登录，操作人为空」，
  而「谁登录的」恰恰是最该记的。
- **教训**：中间件的**执行顺序**决定它能看到什么。这类错误不会报错，只会让某一列一直是空。

### 4.8 验收脚本的 `-Pass` 参数撞了计数器变量

- **现象**：验收脚本一启动就报 `'++' 运算符仅适用于数字。操作数为 'System.String'`，
  然后直接退出，看起来像「服务没起来」。
- **根因**：参数 `[string]$Pass` 与计数变量 `$script:pass` **在 PowerShell 里是同一个变量**
  （变量名大小写不敏感），于是 `$script:pass++` 变成对字符串自增。
  报错点在 `Check()` 函数里，完全看不出是参数名的锅。
- **修法**：参数改名 `$Password`。同类风险：`$Profile`、`$Host`、`$Input`、`$Args`
  都是 PowerShell 自动变量，脚本里不要当普通变量用（本轮早先还踩过一次 `$profile`）。
- **教训**：PowerShell 的变量作用域用冒号区分，但**名字本身不区分大小写**，
  大小写不同不代表不同变量。

### 5.1 界面改版（第二轮）

第一版只做到「信息齐全」，评审意见是**表现太素**：所有页面都是「白卡片 + 表格 + 数字」，
等级只靠一个彩色小 chip 表达，一张图上也没有任何地理参照。改版在**不推翻设计令牌**的前提下
做三件事：

1. **补齐视觉基元**：`Icons`（25 个内联 stroke 图标，离线可用且跟随文字色）、
   `Sparkline`（Catmull-Rom 平滑，折角太硬像噪点）、`Gauge`/`MiniRing`、
   `StatCard`（小标签→大数字→变化徽标→迷你曲线四层）、`Meter`（带阈值刻度）、
   `Tracker`（GitHub 贡献图式时段条）、`EmptyState`/`Skeleton`/`Legend`。
2. **给结论一个视觉位置**：一张图顶部加「态势摘要」条（底色直接取最高等级渐变），
   回答「现在最严重的是哪一级、哪个站点」；站点详情把综合分做成表盘而不是一行数字；
   三因子用带刻度的 Meter 而不是进度条，让「离下一档还有多远」可读。
3. **把理由搬到现场**：一张图右侧新增「值班关注清单」，按综合分排序并**直接引用研判依据原文**
   （峰值/超阈时长/趋势/综合分）。表格能给数值，但值班员真正要看的是这句人话。

改版中修掉的界面问题：

1. **站点卡片被拦腰截断**：右侧站点列表原本是 `max-h-[560px] + overflow-auto`，
   第 4 张卡片永远被切一半。值班时最想一眼看全的恰恰是「还有哪些站点在报警」，
   把它们藏在滚动条后面是本末倒置 → 改为全展开；容器加高后地图改 `sticky` 吸顶，
   站点卡改两列，一屏内的信息密度反而更高。
2. **`04-alerts` 空白**：第一次截图时验收脚本刚好把积水清零了，预警已全部解除。
   这不是 bug，是**截图时机**问题 → 重截前先注入一场暴雨。
3. **散点图标题压住 y 轴名**：ECharts 的 `title.left='left'` 与 y 轴 `name` 默认都在左上角，
   两者叠在一起 → 去掉图内标题，把「N 对样本」写进卡片副标题。
4. **「合计积水」是个没有物理含义的数字**：态势摘要里原本把 10 个站点的水深相加
   （10 × 0.45m = 4.5m）。各站是独立汇水单元，深度不能相加——这个数越大只说明
   「站点多」，不说明「水多」。改为 **最深受水**（`max` 而不是 `sum`），
   值班要看的是「最深的那个点有多深」。
5. **导航项「站点详情」名不副实**：点进去看到的是 10 个站点的列表，
   详情在下一层 → 改名为「站点列表」，与页内标题一致。
6. **两处 TS 严格模式坑**（构建期就拦住，没进产物）：`SERIES` 若写 `as const`，
   `SERIES[k]`（k 为 string）报 TS7053 → 改 `Record<string, string>`；
   `reduce` 的初始值若写成 `reduce<string>`，传给 `LEVEL_RANK[...]` 也报 TS7053 →
   用 `reduce<Level>(..., 'none')`。

#### 5.2.1 视觉语言统一（末轮）

大屏第二轮评审意见是「数据展示还是有点粗糙，而且地图背景的设计和前面前端画框不是同一个风格」。前者是排版节奏，后者是根本问题：**地图是插画风填色 + 金色虚线，白卡是克制 UI**，两种语言并置。

修法一句话：**地图降级为底图，颜色只留给数据**。地块/街坊/山体/绿地/水系全部收到近白与淡灰蓝（饱和度降两档），主干道虚线从金色 `#E8B24A` 换成界面强调色 `p.accent` @0.26，建筑组团改中性 `#E1E9F2`，站点气泡半径系数 0.34→**0.2**、站名 7.4→6.2px——气泡在倾斜铺满后会被放大约 1.9 倍，它应当是「标记」而不是数据图形。

平面本身也补成了「一块屏」：`borderRadius 20` + 白 30% 描边 + `0 40px 80px` 投影 + `inset 0 0 120px` 压边，与白卡同一套圆角/投影语言（此前它是裸 `div`，所以读作「贴了张地图壁纸」）。

粗糙感的三处来源一并修掉：

1. **内容漏出卡片**——`Panel` 正文只有 `minHeight:0` 没有 `overflow:hidden`，右栏「智能体决策」的 signals 网格与左栏「最近告警」都跑到白卡外面，深色演播室上的小字几乎不可读。加 `overflow:hidden` 后一并解决。
2. **密度条看起来是空白**——空桶高度 3px 且与底色同色。改为每格一条浅底轨道 + 桶内实心柱，并补「左旧 · 右新」的方向说明。
3. **卡片高度与内容量不匹配**——「最近告警」6 行塞在 476px 里空出 300px，改为 11 行且每行 `flex:1 1 0` 均分。

顺带把标题压小（17→14.5px）、加下沿发丝线、删掉左上角两根「半截断线」，`Row` 统一成「淡标签 + 实数值 + 发丝分隔」的表格节奏。

#### 5.2.3 换成真实地图，且整页不留暗区

评审两句：「背景的地图那里太暗了，而且不是接入的真实地图，不要模拟的，而且页面不要暗区。」

三件事一起做：

1. **真实瓦片替代抽象 SVG**。`web/src/board/RealMap.tsx` 自己实现墨卡托投影与瓦片拼接（256px 瓦片、`zoom=15`、中心 `121.2445, 28.6455`），站点按真实经纬度打点。不引 MapLibre/Leaflet——大屏本来就无交互，多带 200KB 只为了铺图不划算。
2. **删掉全部暗色层**。深色演播室背景、四周压暗的 `radial-gradient`、平面底色的蓝灰全删了，最底层改成浅色天光渐变。整个页面现在没有一处暗区。
3. **底图降饱和**。瓦片统一 `filter: saturate(0.22) brightness(1.04) contrast(0.94)`。真实地图的绿地、水系、POI 图标都很抢眼，和预警色打架；降饱和之后街道与水系仍然清晰，但颜色只留给数据。**没有用叠加白纱的做法**：白纱会把路名一起洗掉，降饱和保得住结构。

### 5.2.8 补上「降雨-积水响应」，并修掉一个选错的口径（2026-11-07）

**背景**：`response 降雨-积水响应` 在 `layout.ts` 里有坐标（645×177），但

底部给「雨峰时刻 / 响应时延 / 现在水深」。

**途中发现并修掉了一个选错的口径**（这比组件本身更值得记）：

第一版用「雨峰 → 水峰」的峰对峰滞后。实测 S04 报出
**「水位早于雨峰 20h40m」** —— 物理上不可能的结论。查数据才明白不是 bug，
是**度量选错了**：

```

雨峰 index 253（192.07 mm/h，本场暴雨刚下）
水峰 index   5（5.3836 m，上一场雨的退水尾巴）
→ dt = -1240 min
```

本场积水此刻还在涨、根本没到峰，于是「水峰」被上一场的尾巴顶掉了。
**峰对峰滞后只在单场事件内部成立，跨事件比就是拿上一场的峰比这一场的雨。**

改成**响应时延 = 雨峰 → 积水首次越过蓝色阈值**（排水值班真正关心的那个数，
且不依赖事件有没有达峰）。

**改完仍然报错，第二次修正**：

读起来像水位抢在雨前面涨。

| 情形 | 文案 |
|---|---|
| 窗口起点就在阈上 | `全程在阈值以上，本窗测不出起涨`（不报时长） |
| 中途起涨 | `雨峰后 X 起涨` |
| 起涨确实早于雨峰 | `起涨早于雨峰 X` |

### 5.2.9 告警密度卡的三处修补（2026-11-07）

`density 近 24 小时告警密度` 这张卡在截图里被反复跳过，仔细读代码发现三件独立的事：

**① 写死高度又覆盖了版面（老问题复现）**

```jsx
<Panel title="近 24 小时告警密度" ... style={{ height: 92 }}>
```

版面给这块的是 `R(12, 533, 292, 116)`，而面板自己写死 `92` ——
`Widget` 会把面板设成 `height:100%`，**写死的 92 会覆盖它**，卡里 24px 是空的。
这与 `多类别对比` 那次（`style={{height:190}}` ／ 容器 161px）是同一个 bug，
README 里那条「卡片高度由版面求解给、不许写死」就是为此立的。
**教训：这条纪律要靠 `measure-overflow` 复测来兜底** —— 它当时报的是 80/80，
**看起来完全正常**，因为多出来的 24px 是父容器留的空白，不是卡片内部溢出。

**② 三元判断两个分支同值**

```jsx
background: n === 0 ? p.panelLine : isNow ? p.level.red : p.level.red
```

`0 0 0 1px ${p.levelInk.red}` 亮描边 + 实心，历史柱按数量降透明度。
**教训：`a ? x : x` 这种写法 `tsc` 不报错、ESLint 多数配置也不报，只能靠读。**

### 5.2.10 四处「死掉的写死高度」（2026-11-07）

上一节修 `density` 的写死高度时，顺手全文扫了一遍，发现**还有四处**：

| 行 | 面板 | 写死的 | 版面给的 |
|---|---|---|---|
| 512 | 此刻态势 | `height: 190` | 233 |
| 539 | 预警构成 | `height: 178` | 214 |
| 645 | 最近告警 | `height: 476, flex:'1 1 476px'` | 407 |
| 1723 | 观测点 | `height: 206` | 183 |

但这四处**实测全都等于版面值**（`measure-overflow` 报 233 / 214 / 407，不是 190 / 178 / 476）。
原因是 `web/src/board/widget.tsx` 的合并顺序：

```jsx
cloneElement(children, {
  style: { ...(children.props.style ?? {}), height: '100%', width: '100%' },
})
```

面板自己的 `style` 在前、`height:'100%'` 在后 —— **`100%` 永远赢**，
所以面板自己的写死高度**今天没有生效**。

**那为什么还要删？**

1. **它们是误导**：读代码的人会以为「此刻态势」高 190，实测是 233。
2. **它们是地雷**：谁只要把这个 spread 顺序调一下、或改成条件注入，
   四处会立刻「复活」并覆盖版面。`多类别对比` 那次溢出 22px 就是这么来的
   （那处写法不同，写死值真的生效了）。

删掉后 `measure-overflow` 的数值**一个没变**（233/214/407 原样），
说明这次改动是纯粹的「让代码与实测一致」，没有行为变更。
同时把 `最近告警` 的 `bodyStyle` 从 `{ overflow:'hidden', flex:1, minHeight:0 }`
收成 `{ overflow:'hidden' }` —— 那两句 flex 已经被 body 默认样式覆盖。

**验证**：`npx tsc --noEmit` 干净 · `npm run build` ✓ 8.20s ·
`measure-overflow.mjs` **22 块 mismatch 0**、几何数值与改动前逐项一致 ·
`_tools/board_layout.py verify` 三套全通过 ·
`acceptance.ps1 -SkipStorm` **PASS 59 / FAIL 0**（`logs/acceptance-20261107-203927.tsv`）。

**这条对「写死高度」纪律的补充**：光看代码不够，要看**合并顺序**。
同样是 `style={{height:N}}`，在不同包装方式下可能是「生效的 bug」也可能是
「不生效的死代码」，而两者都要删 —— 前者修行为，后者修可读性。

### 5.2.11 两张卡「看着像坏了」的可读性修补（2026-11-07）

评审图里有两张卡第一眼像渲染失败，查下来都是**数值正确但读不出来**。

**① 降雨-积水响应：一条贴顶的平线，读不出含义**

S08 的积水深 1.18 m，而红阈只有 0.38 m —— 水深是红阈的 3 倍。
量程按 `max(红阈*1.2, 窗口峰值*1.05)` 算出来 1.24 m，曲线落在画布 ~95% 高度。
**数值完全正确**，但一条贴着顶边的直线，读者分不清是「这里很危险」
还是「图画错了」。

修法分两步：
1. **量程跟"危险程度"走，不跟"窗口极值"走** —— 原来只用窗口极值归一化，
   水深几乎不变的一段会把曲线钉在顶上；现在以红阈为基准。
2. **加四条阈值虚线 + 右侧数值**（与「水位与预测」同一套配色）。
   有了参考线，「曲线在红线上方」就直接读出来了，不用读者心算
   1.18 比 0.38 大多少。

右侧刻度用 **DOM 文字而不是 SVG `<text>`** —— SVG 被
`preserveAspectRatio="none"` 非等比拉伸会把字压扁。

**② 告警生命周期：0 宽的堆叠条看起来像坏了**

样本内两段平均都是 0 时（上报后立即确认又立即解除），条宽 `(0/0)*100%` = 0，
整条看不见。之前加过一个「中性占位条」，但占位条只有 6px 高、
里面的文字 9px，**在那个高度里根本显示不出来**，等于没改。

修法：合计为 0 时**不画条**，直接给一句明确的话
（`可用样本内 上报后即被确认并解除（拆分不出确认/处置时长）`）；
合计 > 0 才画堆叠条。

**这两条的共同教训**：`clientHeight === scrollHeight` 只证明「没被裁」，
**不证明「读得出来」**。一张卡可以完全不溢出，同时因为量程选错、
参考线缺失、或元素小到看不见而毫无信息量。
`measure-overflow` 与 `probe-gaps` 都量不到这一类问题，只能靠**看截图**。

**验证**：`npx tsc --noEmit` 干净 · `npm run build` ✓ 7.69s ·
`measure-overflow.mjs` **22 块 mismatch 0** · `_tools/board_layout.py verify` 三套全通过 ·
`acceptance.ps1 -SkipStorm` **PASS 59 / FAIL 0**（`logs/acceptance-20261107-205511.tsv`）。
截图裁图确认：四条阈值虚线（红0.38/橙0.25/黄0.12/蓝0.04）与右侧刻度可见、
水线明显在四线之上、结论文字与图形不再互相孤立。

### 5.2.12 告警趋势卡：两根巨型色块，与一个 CSS 静默失效（2026-11-07）

截图裁图时发现这张卡被**一整块蓝和一整块红占满**，读不出任何信息。三轮才修好，
每一轮的失败都比上一轮更隐蔽：

**第一轮失败：百分比高度相加 200%**

每个时间格是一个 `flex column`（`height: 100%`），里面**竖着叠两根柱**：

```jsx
<span style={{ height: `${(b.cleared / mx) * 100}%` }} />   // 解除
<span style={{ height: `${(b.raised / mx) * 100}%` }} />    // 新增
```

百分比是相对**父列**算的。当某一格同时有新增和解除、且都等于 `mx` 时，
两根柱各占 100%，**加起来 200%** —— flex 只能挤压或溢出，于是画出两个大色块。

**修法**：一个格子里的两条序列不应该竖着叠。改成**并排两根细柱**
（`flexDirection: 'row'`、各 `flex: 1, maxWidth: 7`），每根最多 100%，语义干净。

**第二轮失败：`max(2px, X%)` 让整条 height 被丢弃**

改完并排后柱子**全部消失**，只剩底部一排 2px 浅灰线。原因是我给高度写了
`height: max(2px, ${(v/mx)*100}%)` —— CSS 的 `max()` 里混用 px 与百分比，
而父级高度是一条百分比链（`height:'100%'` → flex → 百分数）时，
**浏览器解析不出参照基准，把整条声明丢掉**，高度 fallback 成内容高 = 0。

**这类失败最危险的地方是它不报错**：`tsc` 干净、构建通过、`measure-overflow`
也报 0 mismatch（因为父容器高度没变），只有看截图才知道柱子没了。

**修法**：去掉 `max()`，高度只用纯百分比，用 `minHeight: 2` 兜住极小值。

**第三轮：副标题折行 + 柱顶无留白**

- 副标题「每小时新增与解除 · 看这波是在恶化还是在收尾」在 329px 宽的卡里
  **折成两行**，把 header 撑到约 2 倍高，直接吃掉 body 高度。
  缩短为「新增 vs 解除 · 在恶化还是收尾」。
- 红色柱顶到最上沿（`mx` 那根是 100%），**看不出是 9 还是 5**。
  改成柱高乘 0.92 留出余量，并在页脚标出「峰值 N」。

**修好后才看清楚的数据**：这一格红色 5 根、蓝色 4 根，另一格红色 5 根 ——
**原来那「两个大色块」其实是两条不同序列同时打满，不是同一根柱子画错。**

**这一节要记的不是这个卡，而是三类失败的分工**：

| 失败类型 | 谁能发现 |
|---|---|
| 卡片内容被裁 | `measure-overflow` |
| 卡与卡之间空着 | `probe-gaps` |
| **元素画出来但看不见 / 语义失效** | **只有看截图** |

`max(2px, X%)` 被静默丢弃、百分比相加 200%、副标题折行吃掉高度 ——
这三件事 `tsc`、构建、两个测量工具**全都报正常**。

**验证**：`npx tsc --noEmit` 干净 · `npm run build` ✓ 7.91s ·
`measure-overflow.mjs` **22 块 mismatch 0** · `_tools/board_layout.py verify` 三套全通过 ·

### 5.2.13 让主角真的像主角：版面层级 + 两处数据同源

**① 用版面做层级，不装饰单张卡**

让读者以为这张卡坏了。

**② 写坏过一次，被校验器抓到**
第一版脚本用 `re.search(r'horizon: R\(\d+, 715, \d+, 353\)')` 在整个文件上搜，

**③ 阈值标签从 SVG 挪到 DOM**
`TrendChart` 的四个阈值标签原来写在 `<svg>` 里。卡变宽后全部被右边缘切掉 ——
根因是 `preserveAspectRatio="none"` 把 SVG 坐标按容器等比拉伸，而字号不跟着缩放。
改为 SVG 外层的 DOM 绝对定位（`top` 用百分比），彻底与拉伸解耦。

**④ `curSite` 与 `series` 不同源（真 bug）**
「降雨-积水响应」卡计算基准高程与蓝阈用的是 `curSite`（来自 `/api/sites` 与
`overview.row`），而曲线来自 `series`（`/api/sites/{id}/history`）。轮换每 9 秒
切一次站，`detail = useSiteDetail(cur?.site.id)` 在请求返回前**仍是上一个站的数据**
—— 于是曲线是 A 站的、阈值是 B 站的，护栏 `ds[0] >= blue` 随机为真或假。
现场表现就是卡片写着「起涨早于雨峰 20h35m」这种物理上不可能的结论。
修法：基准高程与阈值都改从 `detail.data.site` 取（与 series 同源）。**这是第三次
栽在「两个 hook 的数据不是同一时刻的同一对象」上**，前两次是预测数字与地图配色。

**⑤ 量程注释与代码必须一致**

红阈定尺度、窗口极值只兜底。修后「现在 1.02m」与「红 0.42」的关系一眼可读。

## 6. 已知边界（不作承诺）

- **数据是模拟的**。模拟器参数是手工标定的「看起来对」，不是率定模型，
  不能用于真实工程决策。
- **站点之间没有水力联系**，不考虑上游来水，只有空间降雨差异。
- **发布渠道只有站内弹窗 + 一个 webhook**，没有短信/电话/大屏。
- **鉴权是本机级**：HttpOnly 会话 cookie，`Secure` 故意没设（本机 http 设了浏览器不回传，
  会导致登录死循环），上线必须挂 TLS 并打开。没有 OAuth/LDAP，没有口令复杂度与登录锁定。
- **容器化配置未在本机验证**：本机没装 Docker，`docker-compose.yml` 与两个 Dockerfile
  是按镜像构建逻辑写的，`make up` 这条路没有实测过；`start.ps1` 那条路是实测的。
- **前端单包 1.4MB（gzip 467KB）未做代码分割**。
- **模型是表格型梯度提升树**，不是时序深度模型；60 天样本量下这样更稳。
- `sim/storm` 与 `sim/reset-water` 是**演练专用**接口，生产环境应整段删除。
