> 契约依据：`docs/06-接口设计说明-对接黄岩区城市内涝基础平台.md` §4

## 0. 一页结论

自研接口 A-1~A-9 已落地为代码，统一挂载在 **`/api/aiwater/v1/*`**。
与 v3 原生接口（`/api/*`）**并存且互不迁就**：

| | v3 原生段 | 网关段 |
|---|---|---|
| 路径 | `/api/*` | `/api/aiwater/v1/*` |
| 成功响应 | 裸 JSON | `{"code":"0","msg":"success","data":{...}}` |
| 失败响应 | `{"error":"中文原话"}` | `{"code":"400","msg":"...","data":null}` |
| 错误码 | HTTP 状态码 | HTTP 状态码 + **字符串** `code` |
| 字段命名 | snake_case | camelCase |
| 分页 | 无统一壳 | `{total,pageNo,pageSize,list}` |

**为什么两套不合并**：v3 原生那套被 9 个前端页面和 `openapi.yaml` 依赖，
网关那套是对方平台（AI 水位预测及预警平台）的对接要求。
两边都是已上线的对外契约，改任何一边都会打破已经存在的东西。
所以网关**自写一套响应出口**（`aiwater_envelope.go`），不去动 `respond.go` 的 `writeJSON` / `fail`。

## 2. 三条贯穿全部接口的硬约束

### 2.1 双时钟标注

v3 内部跑的是 **60 倍加速仿真时钟**（`NowTS()` 取自遥测表最大时间戳），
对方平台用真实时间。不标注的话，对方会把仿真时间当真实采集时间去算时序、算时效、算积水量，整条链路就废了。

所以**每个含时间的响应**都同时给出：

```json
"timeBasis": "simulated",   // 时间基准
"issuedAt": 1794313900,      // 仿真时钟秒
"wallClock": 1794313900      // 真实墙钟秒（Unix）
```

对方按真实时间对齐时用 `wallClock`。

### 2.2 预警四级 → 对外三级

| 我方 v3 四级 | 对外三级 |
|---|---|
| `blue` | `low` |
| `yellow` | `medium` |
| `orange` / `red` | `high` |

映射只放在网关，v3 内部四态机与两道「只降不升」硬约束**保持不变**（ADR-0004）。
对外响应同时在扩展字段 `warnLevel` 保留原始四级，**信息不因映射而丢失**。

过滤参数**同时接受两种刻度**：对方传 `high` 能命中我方的 `orange`/`red`，
对方传 `orange` 也能命中。只认一种的话，对方按自己字典传参就会查空。

### 2.3 幂等靠数据库约束

A-6 的 `requestId` 幂等、A-9 的 `(eventId, stage)` 去重，都由**唯一索引 / 主键**保证，
不是应用层的「先查再插」——后者在并发下必然有窗口。

```
0003_gateway.sql:
  CREATE UNIQUE INDEX idx_aiwater_task_request ON aiwater_task(request_id);
  CREATE TABLE aiwater_event (... PRIMARY KEY (event_id, stage));
```

## 3. 逐接口要点

### A-1 预测结果

- 数据源：v3 内存里的最新预测快照（`service.Forecast()`），由引擎每 60 秒推一次。
  **不是**任意历史时刻的查询——历史走 v3 原生的 `/api/eval/pairs` 与 `/api/sites/{id}/history`。
- `beginTime` / `endTime` 按**预测目标时刻**（`predictTime`）过滤。
- 出参里两个容易搞混的字段：
  - `revision` = 修正**前**的预测水位（条款 9-6 要求保留修正前数值，以便与实测对照）
  - `correctionId` = `{pointCode}:{period}:{modelVersion}:{issuedAt}`，幂等键
  - 实测：`revision=1.6404`、`predictLevel=1.6284`、`correction=-0.012` → `1.6404 - 0.012 = 1.6284` ✓
- `confidence` = `1 / (1 + 1.6449·σ / |水位|)`。公式写在我方而不是让对方算，
  是因为对方那边没有 σ；给结论比让两边各算一遍更不容易对不上。
- 风险等级按**该点该预见期的预测水位落在哪一档阈值**判定，而不是复用站点级告警等级——
  同一站点 1h 可能安全、12h 可能越橙，逐点给风险更有用。

### A-2 风险实时

- **只有当前存在预警的点位才进列表**。对方文档写明「无风险返回空列表非报错」——
  如果把无预警站点也塞进来（`riskLevel=low`），对方拿到的是一长串「低风险」而不是他们要的空列表。
- `rainScene` 恒为 `unspecified`：v3 没有雨情场景模型（条款 8-1 是留白）。
  **不编枚举值**——宁可让对方知道「没有」，也不要给一个看起来像真的值。

### A-3 预警记录

- `status` 由我方四态压成三态：`ACTIVE_UNACK→active`、`ACTIVE_ACK→acknowledged`、
  `CLEARED_*→cleared`。原始四态在扩展字段 `state`。
- 一次最多取 1000 条再在内存里过滤分页。演示环境预警表是几十到几百条量级，
  真到十万级需要给 store 加带条件的 count 与 limit，那是另一件事。

### A-4 雨情规则（只读）

- 阈值来自 v3 站点配置，规则版本来自引擎的 `/rules`。
- 引擎不可达时返回 **503**（对方会退避重试），不给降级的半份数据。
- 阈值是**绝对高程**（引擎里的 `thresholds` 是相对基线的水深，对外要加回 `baseLevel`）。
- 红色档没有更高阈值，以引擎的物理上限 `base + 1.5` 收口。

### A-5 模型版本

- `action=list`（默认）只读；`action=switch` 是**写操作**：
  - 必须带 `versionId`；
  - 必须带 `confirm=true` 做**二次确认**。
    切换模型会让所有站点的预测曲线与告警等级当场改变，而对方 SDK 的重试逻辑会重复发同一个请求；
    没有二次确认，等于让一次网络抖动变成一次静默的线上变更。
  - 切换动作落进既有审计表（`Audit` 中间件对所有 `/api/` 下的 POST 生效）。

### A-6 / A-7 异步任务

- A-6 立刻返回 `taskId` + `status=queued`；结果经 A-7 轮询或 `callbackUrl` 回调。
- `requestId` **必填**：没有它，对方 SDK 重试一次就会开出第二个任务，两边看到的任务数对不上。
- 执行器是**进程内**的：从队列取任务 → 读当前预测快照 → 产出结果行 → 落库 → 投递回调。
  这不是「假的异步」——任务确实落库、状态真的迁移（`queued→running→success/failed`）、结果真的可查，
  只是执行体不是独立算力集群。
- A-7 的 `errorCode` 枚举：`INPUT_MISSING` / `MODEL_UNAVAILABLE` / `TIMEOUT` / `QUOTA_EXCEEDED` / `INTERNAL`。
  区分「模型不可用」（系统故障）与「输入没命中」（参数问题）很重要——
  对方的重试策略对这两者的处理完全不同。
- `resultUrl` 恒为空串：当前实现不落结果文件，结果直接放在 `resultList` 里。
  给一个打不开的 URL 会让对方误判成「还在生成」。

### A-8 事件生命周期

数据来自两处并按操作时刻归并：

1. `aiwater_event` 表——A-9 收到的对方事件（发现/复核/核销）；
2. `warning_event` 表——我方预警四态派生：升起=发现、确认=复核、解除=核销。

只给其中一份都会漏掉一半：只给 A-9 的是对方自己的数据（对我方没增量），
只给预警派生的是我方数据（对方看不到他们推过来的事件）。

### A-9 事件接收

三条硬约束，全部来自对方平台的回调约定：

1. **免平台 Token**：这是对方 ICM → 我方的入站回调，对方不会带它自己的 accessToken
   （那是给我方调它时用的）。但不能因此不设防——用**共享密钥验签**替代 Token。
   - 请求头 `X-AIWater-Signature` 携带 `HMAC-SHA256(WL_AIWATER_EVENT_SECRET, 原始报文体)` 的十六进制值
     （可带 `sha256=` 前缀）。
   - 未配置 `WL_AIWATER_EVENT_SECRET` 时放行，但响应里 `signatureVerified=false`。
2. **幂等**：主键 `(eventId, stage)`。同一事件的同一阶段重复推送只留一条；
   同一事件的不同阶段都要留——那正是「全生命周期」的含义。
3. **必须返回 HTTP 200**：对方平台按状态码判定投递是否成功，非 200 会触发它的重试。
   同一个事件被反复推几十次，幂等表虽然能挡住重复入库，但对方的重试队列会把本接口打满。
   所以验签失败、报文非法也一律回 200，失败信息放在响应包的 `msg` 里
   （那是给对方**业务侧**看的，与传输层的「送达与否」是两件事）。

报文形态兼容：单对象、对象数组、`{list:[...]}`、`{events:[...]}`、`{data:[...]}` 五种都收；
时间兼容 ISO 8601 字符串与 Unix 秒（数字、毫秒都认）。

## 4. 配置

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `WL_AIWATER_TOKEN` | 空 | 网关令牌。空 = 不校验（本机演示态）；对外暴露**必须**设置。支持 `Authorization: Bearer` 与 `X-AIWater-Token` 两种头。 |
| `WL_AIWATER_EVENT_SECRET` | 空 | A-9 事件验签共享密钥。空 = 放行并标注 `signatureVerified=false`。 |

两者**分开**是刻意的：A-9 是对方推给我方的入站回调，对方不会带它自己的 accessToken，
只能靠共享密钥验明来源。
