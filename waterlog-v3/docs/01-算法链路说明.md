# 算法链路说明

> 这份文档回答一个问题：**从一滴雨到一条红色预警，中间到底算了什么。**
> 每一段都给出公式、参数取值和"为什么这么选"，方便逐条追问。

---

## 0. 交付边界

老师给的要求里明确写了"算法链路必须真，数据源可模拟"。所以本系统的定位是：

| 部分 | 状态 |
|---|---|
| 多源数据融合 → 特征工程 | **真算**，47 维，训练与推理共用同一套代码 |
| 多预见期趋势预测（1/3/6/12h） | **真算**，四个独立模型 + 三个对照模型 |
| 三因子联合研判 | **真算**，权重/阈值/最短持续全部可配置 |
| 多源协同滚动修正 | **真算**，在线更新，有防呆闸门 |
| 预测 vs 实际对比与校准 | **真算**，落库、自动结算、三种口径评估 |
| 数据源 | **模拟**，内置双面积水库水文模拟器 |

接真实数据只需实现 `engine/app/sim.py` 里 `Simulator.advance()` 的同构接口
（返回 `step / rain / level / quality / rain_fc_1h / rain_fc_3h / rain_fc_6h / rain_fc_12h`），
下游全部不用改。

## 1. 数据层：水文模拟器

### 1.1 为什么是双面积水库模型

内涝的本质是一句话：**汇水区产流 > 管网排水 + 漫流出流，水在低洼处累积。**

所以模型用两个面积：汇水区 `A_catch`（雨水从哪儿来）和积水区 `A_pond`（水积在哪儿）。
这比随机游走或正弦波强的地方在于，它天然产生真实水文过程线的四个特征：

- **快速上涨**（雨强峰值时产流远大于排水）
- **峰值滞留**（雨停后管网仍在满负荷排）
- **指数退水**（`weir = k·h^1.5`，水越浅排得越慢）
- **管网顶托**（外江水位高时排水能力打折）

### 1.2 方程

每个 5 分钟步长：

```
runoff = rain / 1000 · (STEP_MIN/60) · A_catch · impervious        [m³]
bw     = clip(backwater · min(1, 近3h累计雨量/45), 0, 0.85)         [顶托系数]
eff    = clip(1 − 0.35·min(h/0.40, 1), 0.45, 1.0)                   [效率，水越深越差]
drain  = drain_cap/1000 · (STEP_MIN/60) · A_catch · eff · (1−bw)    [m³]
drain  = min(drain, h · A_pond)                                     [不能抽走不存在的水]
weir   = k · max(h,0)^1.5 · DT_SEC                                  [m³]

widen    = 1 + 6 · max(0, h − spill) / max(spill, 0.05)             [漫溢拓宽]
A_eff    = A_pond · widen
h       += (runoff − drain − weir) / A_eff
level    = base_level + h + 传感器噪声
```

`spill` 取红色阈值。**漫溢拓宽是让极端暴雨不算出 3~4 米积水的关键物理约束**：
真实内涝一旦超过红色阈值就会向相邻街区漫溢，等效调蓄面积随水深扩大，峰值被削掉。
没有这一项，早期版本在 160mm/h 暴雨下算出的水深是 3~4 米（相当于两层楼），
加上之后回落到 0.58~0.79 米的合理区间。

### 1.3 降雨过程

不是均匀下雨，而是泊松到达 + 非对称高斯过程线：

- 到达间隔 ~ `Exponential(1/rate)`，`rate = 0.85 · 季节系数 · 日变化系数`（场次/天）
- 历时 ~ `LogNormal(log 45min, σ=0.5)`，截断到 30min ~ 8h
- 峰值 ~ `LogNormal(log 26mm/h, σ=0.62)`，截断到 3 ~ 240 mm/h
- 7% 概率是极端场次，峰值再乘 2.0~3.4
- 上升段 `p^0.8`，下降段 `exp(−((p−rise)/tail)²)`——先急后缓，符合对流性降水

季节（夏季 1.2 / 冬季 0.25）、日变化（14–21 时 1.55 倍）都做了调制。

### 1.4 四路数据源，都是模拟器同一时刻派生的

| 数据源 | 怎么来 | 加了多少"真实世界的脏" |
|---|---|---|
| 实时监测水位 | `base + h` | 传感器噪声 σ=0.008m；1.2% 概率劣化（quality=0，读数卡住） |
| 实时监测雨量 | 站点空间差异 `spatial × wobble` | 各站点雨量不同，不是全城一个数 |
| 历史降雨/积水 | 就是过去 60 天的序列 | — |
| 气象预报 | **真值 × 系统低估 × 随机误差** | `bias = 1 − 0.04√(k/12)`、`σ = 0.10√(k/12)`，预见期越长越不准 |

气象预报这一条很重要：它让"预报雨量"和"实测雨量"必然有差，**多源协同修正才有事可做**。
如果预报是完美的，修正模块就是个摆设。

### 1.5 标定结果与局限

60 天 × 10 站点标定后：峰值水深 0.58~0.79m，p50≈0.001m，
超蓝/黄/橙/红阈值的时间占比 0.8~3.1% / 0.5~2.0% / 0.4~1.6% / 0.1~1.3%，
降雨 >20mm/h 的时间占比 3.2%。量级合理。

**必须承认的局限**（答辩时主动说，别等人问）：

1. 不是 SWMM/MIKE 那种率定模型，参数是手工标定的"看起来对"，不能用于真实工程决策；
2. 管网按设计能力恒定排水，只有一个效率系数表达淤积/顶托，**没有管网拓扑**；
3. 降雨是随机过程，不是真实气象再分析数据；
4. **站点之间没有水力联系**，不考虑上游来水，只有空间降雨差异。

## 2. 特征工程：47 维

全部在 `engine/app/features.py` 的 `FEATURE_NAMES` 里声明，
训练、推理、重要性分析统一用 `col("name")` 按名字取列。
**这条约束是踩过坑换来的**：早期代码里写 `Xva[:, 4]` 以为取 `d_level_12`，
实际 4 号列是 `level_lag6`，线性基线误差算成 9~111 米，融合权重全被带偏。

| 组 | 特征 | 为什么需要 |
|---|---|---|
| 水位滞后 | `level_lag0/1/2/3/6/12` | 当前状态 + 短期惯性 |
| 水位差分 | `d_level_1/3/6/12` | 涨得多快，比绝对值更重要 |
| 形态 | `slope_1h`、`accel`、`level_max/min/range_3h` | 一阶、二阶趋势与近期波动幅度 |
| 实时雨量 | `rain_now`、`rain_max_1h` | 此刻下多大 |
| 累计雨量 | `rain_sum_30m/60m/180m/360m/720m/1440m` | **内涝是累积效应，6 个时间尺度都要有** |
| 气象预报 | `fc_1h/3h/6h/12h`、`fc_excess_3h/6h` | 未来会下多少；`excess` 是超过排水能力的部分 |
| 站点属性 | `impervious`、`drain_mm_h`、`catchment_ha`、`pond_ha`、`pond_ratio` | 同样的雨，不同站点涨得不一样 |
| 阈值上下文 | `base_level`、`thr_blue/yellow/orange/red`、`headroom_red`、`saturation` | 离危险还有多远 |
| 时间 | `hour/dow/month` 的 sin/cos | 排水调度有昼夜差异（三角函数编码避免 23 时→0 时的跳变） |

`saturation`（当前水深 / 红色阈值）是重要性第一名（0.824），
`fc_3h`（0.195）和 `fc_excess_3h`（0.134）紧随其后——
**这说明模型主要靠"已经积了多少水"和"接下来还要下多少"来判断，物理上说得通。**

## 3. 预测模型

### 3.1 预测目标是增量 Δy，不是绝对水位

```
Δy = level[origin + h] − level[origin]
yhat = level[origin] + Δy_pred
```

三个理由：

1. **以实测为锚**，预测曲线与历史曲线在"现在"这个点天然连续，不会出现断裂；
2. 增量比绝对值平稳（站点间基准高程差 3.6~16.3m，绝对值预测等于让模型先学高程再学涨落）；
3. 反归一化就是一次加法，没有误差累积。

### 3.2 四模型同表对比

每个预见期（60/180/360/720 min）各训一个模型，同时训三个对照：

| 模型 | 定义 | 作用 |
|---|---|---|
| 持久化基线 | Δy ≡ 0 | 最笨的预测，**分母** |
| 线性外推 | `slope_1h × h` | 最朴素的"预报员做法" |
| 梯度提升树 | 47 维 → Δy | 主模型 |
| **融合（上线）** | `w·树 + (1−w)·持久化` | 上线版本 |

树模型超参：`HistGradientBoostingRegressor(max_iter=260, learning_rate=0.06, max_depth=6,
min_samples_leaf=40, l2_regularization=1.0, early_stopping=True, validation_fraction=0.12)`。

**为什么融合对象是持久化基线而不是线性外推**：线性外推在退水期会一路外推到负值。
拿它当融合对象等于给系统埋雷。权重 `w` 在验证集上按站点 × 预见期做 21 点网格搜索，
`w < 1` 表示"这个站点这个预见期上树模型并不稳定优于基线，自动保守化"。
实测 60/180/360min 的 w 基本都是 1.0，720min 出现 0.6~0.95 的权重——
**长预见期自动保守，这正是设计意图。**

### 3.3 验证集怎么划：分块交叉验证

一开始用"最后 10 天做验证集"，结果 NSE 出现 −1.137、skill −0.462，看起来模型废了。
查下去发现：那 10 天如果没下暴雨，Δy 几乎恒等于 0，持久化基线误差接近 0，
分母太小，任何模型都会显得很差。

改成 **3 折分块交叉验证**（`_blocks()` 用 `np.linspace` 把时间轴切段，每折轮换验证），
并且**额外单报"事件样本"指标**（预见期末水深 ≥ 蓝色阈值的样本）。

**事件样本这一列是全文档最该看的一列。** 全样本指标会被大量平静时刻稀释：

| 模型 | 1h event_skill | 3h | 6h | 12h |
|---|---|---|---|---|
| 持久化基线 | +0.000 | +0.000 | +0.000 | +0.000 |
| 线性外推 | +0.281 | **−0.279** | **−0.583** | **−0.131** |
| 梯度提升树 | **+0.700** | **+0.536** | **+0.491** | **+0.306** |

线性外推在暴雨时段是**负技能**的（比"水位不变"还差），树模型是 +0.3~+0.7。
这就是"趋势预测模型有价值"的直接证据。

### 3.4 不确定性区间

残差标准差按站点 × 预见期分别统计（σ 是异方差的，不同站点不同预见期差一个量级），
90% 区间用 `z = 1.6449`。区间做两层钳制：

1. **物理约束**：水位不低于基准高程，不高于 `base + 1.5m`；
2. **修正量钳制在 ±3σ**：滚动修正器即使失效，也不允许把曲线推出置信带。

上线实测 PICP90 = 92.4% / 96.6% / 95.8% / 94.7%，标定良好（目标 90%）。
对照线性外推的 PICP90 只有 26.5~49.3%，**区间严重欠覆盖**——它的区间是假的。

### 3.5 曲线加密用 PCHIP

四个预见期只有四个点，画到图上要插值。选 **PCHIP（Fritsch-Carlson 单调保形）**：

- 线性插值：有折角，不像水位过程线；
- 三次样条：会 overshoot，**在峰值附近插出假峰**，直接导致误报；
- PCHIP：保单调、不过冲，插出来的曲线不会骗人。

加密到 5 分钟粒度（`arange(0, 721, 5)`），下界取 `min`、上界取 `max`，保证包住端点。

### 3.6 指标定义

| 指标 | 定义 | 读法 |
|---|---|---|
| RMSE / MAE | 常规 | 单位米 |
| NSE | `1 − SSE/SST` | 纳什效率系数，>0.7 算好 |
| skill | `1 − RMSE/RMSE_基线` | **>0 才比基线强**，这是主指标 |
| PICP90 | 实际值落在 90% 区间内的比例 | 目标 90%，太高说明区间过宽 |
| PINAW | 区间宽度 / 观测幅度 | 配合 PICP 看，防止"把区间画到无限宽" |
| CRPS | 连续排序概率得分 | 同时惩罚偏差与区间，越小越好 |

## 4. 三因子联合研判

### 4.1 不是"过阈值就报警"

```
score = w_peak·peak + w_dur·duration + w_trend·trend
      = 0.45·peak + 0.35·duration + 0.20·trend
```

| 因子 | 含义 | 归一化方式 |
|---|---|---|
| `peak` | 研判窗口内预测峰值水位 vs 各级阈值 | 分段映射到 0~1.5 |
| `duration` | 预测超过阈值的累计时长 / `duration_saturation_min`(180min) | 线性到 1 |
| `trend` | 窗口内水位变化斜率，映射到 `0~1`（跨度 `trend_score_span`=0.5 m/h） |

再按 `score_cutoffs`（蓝 0.22 / 黄 0.40 / 橙 0.60 / 红 0.78）分档。

**为什么是三因子而不是单看峰值**：同样涨到橙色阈值，
"涨上去 5 分钟就退"和"涨上去压 3 小时"是两件事；
"正在快速上涨"和"已经在退水"也是两件事。三个因子分别回答
**会多高、会多久、还在不在涨**。

### 4.2 两道硬约束只降不升

1. **最短持续门槛**：超阈持续时间不足 `min_duration_min[level]`（蓝 20 / 黄 30 / 橙 45 / 红 60 min）
   时，等级封顶。短时尖峰不等于持续内涝。
2. **趋势跨档**：斜率 ≥ `+0.25 m/h` 升一级（还在快速上涨，宁可提前），
   ≤ `−0.15 m/h` 降一级（已经在退，不必惊动）。

这两条都写进 `blocked_by` 字段，前端会显示"因为持续时间不足 60min，红色封顶为橙色"，
**降级必须说得出理由**，不能悄悄降。

### 4.3 参数可配置

`engine/data/rules.json`：权重、分档、最短持续、趋势门槛、研判窗口、`min_level_for_alarm`。
前端「规则配置」页可改，`PUT /api/rules` 后**下一轮预测立即用新规则重算全部站点**，不用重启。

## 5. 多源协同滚动修正

`RollingCorrector` 按 (站点, 预见期) 维护两个指数加权统计量：
系统性偏差均值 `err_mean` 与绝对误差 `err_abs`（`alpha = 0.15`）。

```
gain  = clip(1.6 · err_abs/0.05 · 0.25, 0.05, 0.6) / (1 + h/360)
delta = gain · err_mean · 1/(1 + h/240)
yhat  = clip(model_yhat + clip(delta, −3σ, 3σ), base, base + 1.5)
```

三个设计决定：

1. **新息取系统性偏差，不取瞬时观测差。**
   用瞬时差等于把传感器噪声（σ=8mm）直接灌进预测曲线，预测会跟着噪声抖。
   系统性偏差是"模型整体偏高还是偏低"，才是有用的信号。
2. **按预见期衰减**（`1/(1+h/360)`、`1/(1+h/240)`）。
   12h 的预测本来就该有更大自由度，不该被 1h 的偏差强行拉齐。
3. **启动时离线回放 3 天预热**（`warmup_corrector`）。
   否则刚启动的第一个小时修正强度是 0，等于白跑。

**协同的第二个来源是气象预报修正**：`rain_sensitivity()` 用无截距最小二乘回归出
每个站点"雨量 → 水位"的弹性 β（钳制 0~0.02），把预报雨量与实际雨量的差异折算成水位增量。
这就是"多源协同"里"实时监测修正 + 气象预报修正"两路的落地。

### 5.1 这里踩过一个致命 bug，值得记下来

`warmup_corrector` 里 `_predict()` 返回的是**增量 Δy**，却被直接当成绝对水位去比：

```python
yhat = self._predict(X, sites, hstep)          # 错：这是 Δy
err = yhat − ds.level[o + hstep, sites]
```

结果误差均值算成 **+7.85m**（差不多就是站点基准水位），修正器每轮加 3.2 米，
S01 的预测被顶到 `base+1.5` 上限，预警直接判红。

修法：`yhat = ds.level[o, sites] + self._predict(X, sites, hstep)`。

**教训：同一个系统里"水位"和"水位增量"必须是两种类型，不能都叫 float。**
现在所有预测相关代码都显式命名 `yhat`（绝对）与 `delta`（增量），并在文档里标注。

## 6. 评估与校准

### 6.1 每条预测都落库

`prediction` 表：`issued_at, target_at, site_id, horizon_min, model, yhat, yhat_raw,
origin_level, lower, upper, actual, evaluated_at`。

到预见期走完后 `settle()` 自动回填 `actual`。**`origin_level` 是关键字段**——
它是发布预测时刻的实测水位，也就是持久化基线的锚点。

### 6.2 三种评估口径

| 口径 | 数据 | 用途 |
|---|---|---|
| 离线 3 折交叉验证 | 60 天历史 | 训练时的整体精度 |
| **事件样本** | 预见期末水深 ≥ 蓝阈的样本 | 最该看的一列 |
| 在线滚动 | 近 N 小时已结算的真实预测 | 上线后到底准不准 |

### 6.3 skill 口径的坑（踩过）

在线 skill 一度显示 0.9826 / 0.9403 / 0.9462 / 0.9316，明显是假指标。原因：

```python
persist = sqrt(mean((act − act.mean())**2))    # 错：用实际值的标准差
```

跨站点基准高程差 3.6~16.3m，远大于预测误差，用"实际值的标准差"当分母，
skill 必然被虚抬到 0.98。

改成 `persist_err = origin_level − actual`（发布时刻实测 vs 实际），
修后 1h skill ≈ 0.32~0.54，与离线 60min 的 +0.503 同量级，合理。

**教训：skill 的分母必须是"同一时刻、同一口径的基线预测"，不能是数据的离散度。**

### 6.4 校准闭环

在线 skill 掉了 → 前端「模型评估」页点"触发重训"（或 `POST /api/retrain`）→
后台线程训练新版本 → `latest.txt` 指针热替换 → 旧版本指标留档对比。
规则不合理就改规则，不用改代码。两条路都不需要重启服务。

## 7. 智能体值班

`engine/app/agent.py`，每个预测周期对每个站点做一次调度决策：

```
输入信号：rain_now(雨强)、fc_3h(预报雨量)、slope_1h(水位斜率)、
         depth(积水深)、quality(传感器质量)、saturation
触发阈值：RAIN_NOW_TRIGGER=0.8 mm/h、RAIN_FC_TRIGGER=3.0 mm、
         SLOPE_TRIGGER=0.04 m/h、QUIET_SKIP_MIN=6（连续静默轮次）
```

输出 `AgentDecision(should_forecast, model, gain, reason, signals)`：

- 有雨 / 在涨 / 已积水 → `should_forecast=True`，`model="blend"`，理由写明哪个信号触发；
- 传感器劣化（quality=0）→ `model="linear"`，降级到线性兜底并说明原因；
- 长时间静默 → 常规周期，不做主动加算。

这是"智能体"在这个系统里的具体形态：**不是对话机器人，而是每一轮自己判断
"这个站点现在值不值得算、该怎么算、算出来能不能信"**。
决策连同信号全部入库，前端「模型评估」页可查。

## 8. 一句话总结链路

```
降雨（模拟器）
  → 四路数据源（实测水位/实测雨量/历史/气象预报）
  → 47 维特征工程
  → 4 个预见期的梯度提升树（预测增量 Δy）
  → 与持久化基线按站点×预见期融合（w 网格搜索）
  → 滚动修正（系统性偏差 + 气象预报弹性，钳制在 ±3σ）
  → PCHIP 加密成 5 分钟曲线 + 物理约束钳制
  → 三因子研判（峰值 0.45 / 持续 0.35 / 趋势 0.20）
  → 两道降级约束（最短持续 + 趋势跨档）
  → 预警等级 → Go 侧四态机 → SSE → 前端一张图
  ↑                                              ↓
  └──── 预测落库 → 自动结算实际值 → skill 下降 → 重训/改规则 ────┘
```
