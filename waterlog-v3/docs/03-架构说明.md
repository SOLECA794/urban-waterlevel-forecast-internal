## 二、为什么是三个进程

| 关注点 | 浏览器 | Go API | Python 引擎 |
|---|---|---|---|
| 延迟敏感 | 是 | 是 | 否 |
| CPU 密集 | 否 | 否 | **是**（训练 90 秒） |
| 依赖重量 | 1.4MB bundle | 40MB 静态二进制 | 200MB+（numpy/pandas/sklearn） |
| 需要水平扩 | 是（CDN） | 是 | 否（有状态模型） |
| 挂了会怎样 | 白屏 | 全站不可用 | 预测停更，历史与遥测仍在 |

**关键取舍**：训练期间 API 完全可用。`/api/health` 的 `engine_ok` 变 false，前端渲染「预测滞后」而不是空白页。这是拆进程最主要的收益 —— 而重训恰恰发生在「值班员觉得模型不准」的时候，也就是最不能不可用的时候。

详见 [ADR-0001](adr/0001-引擎与API进程分离.md)。

## 三、一次心跳的完整链路

60 倍速下，每 5 秒墙钟 = 5 分钟仿真时间：

```
① 引擎 _loop() 醒来（每 WL_TICK_SEC=5s）
   ├─ sim.advance(1)                    # 降雨过程 → runoff/drain/weir → 水位
   ├─ 追加到 LiveBuffer                 # 特征缓冲滚动窗口
   ├─ POST /api/ingest/telemetry        # 10 站点 × 1 时刻
   └─ 每 12 tick 落盘 sim_state.npz + sim_clock.json

② Go API ingestTelemetry
   ├─ store.InsertTelemetry             # 幂等 upsert，PK(ts,site_id)
   └─ hub.Broadcast("telemetry")        # SSE 帧

③ 浏览器收到 telemetry 事件
   ├─ 节流 800ms
   └─ invalidateQueries([overview, health])   # 只有这两个 key 失效

④ 引擎每 WL_FORECAST_EVERY_SEC=60s（= 60 分钟仿真时间）
   ├─ settle()                          # 把到期预测与实测配对，结算进 eval.sqlite
   ├─ 每站点：
   │   ├─ agent.decide()                # 要不要加算、用哪个模型、修正增益
   │   ├─ build_features(47 维)
   │   ├─ 4 个预见期 × (GBR 增量 + 融合权重 + 滚动修正)
   │   ├─ σ 区间 → clip 到物理约束
   │   ├─ PCHIP 加密到 5 分钟（保形插值，不 overshoot）
   │   ├─ rules.assess_from_forecast()  # 三因子 → 等级
   │   └─ store.add_predictions()       # 落库待结算
   └─ POST /api/ingest/forecast

⑤ Go API ingestForecast
   ├─ store.SaveForecast                # 全站快照（单条 payload）
   ├─ store.InsertDecisions             # 智能体决策日志
   ├─ 逐站点 store.SyncWarning()        # 四态迁移
   │   └─ 动作 raised/upgraded → notify.Dispatch()
   └─ hub.Broadcast("forecast") + 逐条 Broadcast("warning")

⑥ 浏览器
   ├─ invalidateQueries([overview, forecast])
   └─ warning 事件 → invalidateQueries([alerts, overview])
```

**为什么引擎是推、API 是拉**：引擎掌握仿真时钟，它知道「该推进了」；API 只在启动时拉站点元数据、用户点重训时发起请求。反过来做（API 轮询引擎）会让时钟归属变模糊，重启时两边对不齐 —— 这是实际踩过的坑，见 [ADR-0002](adr/0002-仿真时钟与墙钟分离.md)。

## 四、数据流：从原始信号到一条预警

```
多源数据
  ├─ 实测水位（带传感器噪声 σ=0.008m，1.2% 概率劣化）
  ├─ 实测雨强（泊松到达 + 非对称高斯过程线）
  ├─ 气象预报（真值 × 系统性低估(1-0.04√(k/12)) × 随机误差(σ=0.10√(k/12))）
  └─ 历史统计（60 天，由同一模拟器生成）
        │
        ▼  统一特征工程（47 维）
  ├─ 水位动态    level_lag{0,1,2,3,6,12} · d_level{1,3,6,12} · slope_1h · accel
  ├─ 极值        level_max/min/range_3h
  ├─ 雨量        rain_now · rain_max_1h · rain_sum_{30,60,180,360,720,1440}m
  ├─ 预报        fc_{1,3,6,12}h · fc_excess_{3,6}h
  ├─ 站点属性    impervious · drain_mm_h · catchment_ha · pond_ha · pond_ratio
  ├─ 阈值关系    base_level · thr_{blue,yellow,orange,red} · headroom_red · saturation
  └─ 时间        hour/dow/month 三角编码
        │
        ▼  4 个预见期 × 3 个模型 + 融合
  ┌──────────────────────────────────────────────────────────┐
  │ persistence  Δy = 0                    （零假设基线）      │
  │ linear       Δy = slope_1h × h         （线性外推基线）    │
  │ gbr          HistGradientBoosting      （主模型）          │
  │ blend        w·gbr + (1-w)·persistence （按站点×预见期调 w）│
  └──────────────────────────────────────────────────────────┘
        │
        ▼  滚动修正（RollingCorrector）
  innovation = 指数加权系统性偏差（不是瞬时观测差）
  gain       = f(该站点该预见期的历史绝对误差) × 1/(1+h/360)
  applied    = clip(gain × innovation × decay, ±3σ)   ← 防呆闸门
        │
        ▼  PCHIP 保形加密（5 分钟分辨率）
  选 PCHIP 不选线性/样条：线性有折角，三次样条会 overshoot 插出假峰值
        │
        ▼  三因子研判
  peak_norm     = _ratio(峰值积水深, 该级阈值)      → 0~1.5
  duration_norm = 超阈持续 / 饱和时长(180min)       → 0~1
  trend_norm    = 1h 变化率 / trend_score_span      → 0~1
  score = 0.45·peak + 0.35·duration + 0.20·trend
        │
        ├─ 按 score_cutoffs 分档 → blue/yellow/orange/red
        ├─ 硬约束①：持续未达 min_duration_min[级] → 封顶降级（只降不升）
        ├─ 硬约束②：低于 min_level_for_alarm → none（只降不升）
        └─ 趋势跨档：≥0.25m/h 升一级，≤-0.15m/h 降一级
        │
        ▼
  预警事件（四态机）+ 智能体决策日志 + 待结算预测
```

完整算法说明见 [01-算法链路说明.md](01-算法链路说明.md)。

## 五、改动落在哪一层

这是分层唯一真正的检验标准：**知道一个新需求该改哪里，且不该改哪里。**

| 需求 | 改哪 | 不该改哪 |
|---|---|---|
| 加一个站点 | `engine/waterlog/config.py` 的 `SITES` + `api/internal/domain/sites.go` 的 `builtinSites` | 任何页面、任何 adapter |
| 改某站阈值 | `config.py` 的 `Site.thresholds`，然后**重训**（阈值参与特征工程） | rules.json、任何页面 |
| 改研判策略（权重/分档/最短持续） | 规则配置页，或 `PUT /api/rules` | 代码、模型 |
| 加一个预警处置动作 | `domain/alert.go` 的 `dispositionNext` + `domain/assessment.ts` 的 `TRANSITIONS` + 页面按钮 | store、四态机 |
| 换模型算法 | `engine/waterlog/ml/models.py` | API、前端、契约 |
| 加一个 API 字段 | `domain/types.go` + `data/dto.ts` + `data/adapters.ts` | 页面（除非页面要用它） |
| 改页面视觉 | `components/primitives/` 或 `styles/tokens.css` | domain、data、view |
| 改某屏显示哪些字段 | 对应的 `view/useXxx.ts` | 其它屏 |
| 接真实数据源 | 把 `POST /api/ingest/telemetry` 的调用方从引擎换成采集器 | 其它全部 |
| 加通知渠道 | `api/internal/service/notify.go` 的 `builtinChannels` + `deliver()` | 预警四态机 |
| 加一个角色或权限点 | `domain/user.go` 的 `RoleRank` + `domain/auth.ts` 的 `MIN_ROLE`（**两处必须同源**）+ 路由上的 `RequireRole` | handler 内部（鉴权写在路由层） |
| 加一个审计动作的人话摘要 | `httpapi/authmw.go` 的 `summarize()` | 各 handler（审计是中间件自动做的） |
| 加一个需要审计的接口 | 什么都不用改（写方法 + `/api/` 前缀自动记） | — |

**反例（这些都是重构前真实存在过的）**：
- 「改某站阈值」需要改三个页面里的 `|| 0.46` 兜底 —— 现在只需要改 `config.py`。
- 「加一个排序方式」需要在两个页面各写一遍排序 —— 现在是 `useWatchlist(sort)` 一个参数。
- 「接口加字段」需要动 500 行的页面文件 —— 现在改 adapter，页面不动。

## 七、鉴权、角色与治理

### 7.1 三段式：认证 → 授权 → 审计

```
请求 → RequestID → AccessLog → Recover → CORS → Audit ─┬─ 公开段（/health、login）
                                                      ├─ ingest 段（RequireIngestToken）
                                                      ├─ 只读段（Authenticate）
                                                      ├─ operator 段（RequireRole("operator")）
                                                      └─ admin 段（RequireRole("admin")）
```

**鉴权写在路由层，不写在 handler 里。** 理由很实际：写在 handler 里时，
「这个接口该谁能调」散在十几个函数的第一行，加一个接口忘了写就是一个越权洞，
而且从路由表上看不出来。现在打开 `router.go` 就能读到完整的权限矩阵。

### 7.2 会话为什么不是签名 cookie

会话是**不透明随机令牌**（32 字节 crypto/rand）存在 `app_session` 表里，
库里只存它的 SHA-256 摘要。签名 cookie（JWT 那类）看着更"现代"，但在这里有两个实际代价：
无法在服务端撤销（改口令、停用账号后旧 token 仍然有效到过期），以及
`WL_SESSION_SECRET` 一旦泄漏就等于全站失守且无法补救。改成查表后，
「改口令 / 停用账号 → `DeleteUserSessions` → 下一个请求就 401」是天然成立的。

摘要而不是明文：库被拖走时，摘要不能直接当 cookie 用。

### 7.3 时间轴：会话走墙钟，业务走仿真时钟

| 用途 | 时钟 | 理由 |
|---|---|---|
| 会话过期、`pruneSessions` | 墙钟 `time.Now()` | 用户感受到的是真实时间；仿真时钟 60 倍速会让 12 小时会话在 12 分钟墙钟后失效 |
| `last_login_at`、审计 `at`、预警时间 | 仿真时钟 `NowTS()` | 它们要和遥测、预测、预警事件排在同一条时间轴上，否则「10-21 登录、11-11 最后登录」 |

`Auth.Login(username, password, wallNow, simNow)` 两个都收，就是为了让这条边界显式存在。
这个坑实际踩过：`last_login_at` 一开始用了墙钟，账号页和预警页差了 21 天。

### 7.4 角色是三个，不是两个

`admin` / `operator` / `viewer`。把 operator 和 admin 合成一个角色是最常见的偷懒，
后果是「能确认预警的人也能改研判规则和删账号」。三种角色对应三种真实工作状态：

| 角色 | 能做什么 | 典型使用者 |
|---|---|---|
| `viewer` | 看一张图、站点、预警、模型指标、规则 | 领导、外部门、大屏 |
| `operator` | 确认预警、派单、推进处置、写备注、降雨注入、预演规则 | 值班员 |
| `admin` | 改规则并生效、切换生效模型、重训、管账号、看审计、配推送 | 系统管理员 |

**能力表在两处，必须同源**：后端 `RequireRole` 决定接口通不通，
前端 `web/src/domain/auth.ts` 的 `MIN_ROLE` 决定按钮亮不亮。各写一遍就是
「界面上能点、点了 403」——所以前端那张表是照着后端路由表抄的，改一处必须改另一处。

两条硬约束写在服务层而不是 UI 里：**最后一个可用管理员不能降级或停用**（否则系统再也没人能管），
**不能停用自己或降低自己的角色**（否则误操作当场把自己锁在外面）。

### 7.5 治理：三个"改之前先看看会怎样"的能力

| 能力 | 接口 | 为什么需要 |
|---|---|---|
| 规则影响预演 | `POST /api/rules/preview` | 改分档阈值前先看十个站点会怎么变。**不重新预测**——用同一条已发布曲线重判 before/after，否则分不清变化来自规则还是模型噪声 |
| 模型版本治理 | `GET /api/models/versions`、`POST /api/models/adopt` | 6 个训练版本可查可切。采纳前先 `load_bundle` 验证，坏模型**不切换** |
| 处置闭环 | `POST /api/alerts/{id}/assign|disposition|notes` | 四态回答"预警还成立吗"（模型决定），处置回答"我们做了什么"（人决定） |

两条轴分离的理由见 [ADR-0004](adr/0004-预警四态与处置两轴分离.md)。

## 八、可观测性

**健康检查**：`GET /api/health` 返回三段信息 —— 服务自身、SSE 连接数、引擎状态。`engine_ok=false` 是一个明确的一等状态，不是被吞掉的异常。

**结构化日志**：`WL_LOG_FORMAT=json` 时输出 slog JSON，每条带 `request_id`，可与 nginx 的 `X-Request-ID` 对齐。

**审计**：所有写操作（含失败的）由中间件自动落 `audit_log`，记 actor/role/method/path/status/耗时/IP/request_id + 一句话摘要。只读接口不记。失败的那些恰恰是最需要查的。

**在线评估**：每轮预测落 `prediction` 表，到期后与实测配对，按预见期算 rmse/mae/bias/p95/skill。**skill 的分母是持久化基线**（发布时的实测水位），不是实际值的标准差 —— 用后者会把跨站点高程差（3.6~16.3m）算进基线，skill 虚抬到 0.98。

**前端可信度**：`useTrust()` 把「读数新鲜度 / 预测新鲜度 / SSE 存活」合成一个 `DataTrust`，`TrustBanner` 在非 live 或流断时出现。三种异常（传感器劣化 `quality<0.7`、预测过期、流断开）第一次有了视觉表达。

## 九、故障模式

| 故障 | 表现 | 系统行为 |
|---|---|---|
| 引擎挂了 | `/api/health` 的 `engine_ok=false` | 遥测停更、预测停更；历史、预警列表、处置、审计全部可用；前端显示「预测滞后」横幅 |
| 引擎重启中（训练 90s） | `engine_ok=false` | 同上。旧预测仍在库里，一张图不空白 |
| 引擎重启完成 | 仿真时钟前移 | 从 `max(数据集末尾, sim_clock, API 的 ts, 已发布 issued_at)` 续跑，不倒退 |
| Go API 挂了 | 浏览器请求失败 | 引擎推送失败只记日志不崩（`_post` 捕获异常）；恢复后下一 tick 自动接上 |
| SQLite 锁 | `busy_timeout=5000` | 写操作排队；WAL 模式允许读写并发 |
| SSE 断开 | 前端 `connected=false` | 3 秒后自动重连（EventSource 原生行为）；期间 `TrustBanner` 提示，轮询仍在兜底 |
| 模型版本损坏 | 采纳时 `load_bundle` 失败 | **不切换**，返回 404 原话。坏模型上线比不准的模型危险 |
| 某站传感器劣化 | `quality<0.7` | 智能体把该站降级到线性兜底模型，`FreshnessBadge` 标黄 |
| 会话过期 | 任意请求 401 | `client.ts` 的 `onUnauthorized` 统一把人送回登录页，带上 `from` 回跳。**不这么做的话，二十个 query 各写一遍一定漏一个** |
| 只读账号调写接口 | 403 | 前端本来就不显示那个按钮（`can(user, cap)`），后端 `RequireRole` 再拦一次。两道都要，因为前端可以被绕过 |
| 推送 webhook 超时 | 4 秒超时 | **不重试**。预警要的是及时，4 秒后重试的"2 级橙色预警"可能已经变成 4 级红色，追着发旧的反而误导。失败落 `notify_delivery` 留痕 |

## 十、已知边界

1. **数据是模拟的**。`simulator/` 生成降雨与水位，物理关系真实（双面积水库 + 漫溢拓宽），但不是实测。接真实数据源只需替换 `POST /api/ingest/telemetry` 的调用方。
2. **60 倍速**。仿真时间跑在墙钟前面，所有「现在」必须用 `NowTS()`，不能用 `time.Now()`。生产环境 1 倍速时这套机制退化成恒等映射。
3. **发布渠道只有站内**。`notify` 的 webhook 渠道是接口完整但只做过本地 echo 验证，没有真的对接企业微信/钉钉。
4. **表格树模型，不是时序深度模型**。47 维特征 + 4 个独立 GBR，没有 LSTM/Transformer。理由是 60 天数据量下深度模型过拟合风险高于收益；`fc_3h`/`saturation` 这两个特征已经承担了主要解释力（置换重要性 top2）。
5. **单机 SQLite**。10 站点 / 5 秒一 tick / 每分钟一轮预测，SQLite + WAL 足够。要上多实例得换 PostgreSQL（`store` 层已经隔离，改 DSN 与少量 SQL 方言即可）。
6. **前端 bundle 1.4MB 未分割**。ECharts 全量引入占了大部分。要做代码分割的话，`charts/` 目录下三个图可以各自 `lazy()`。
7. **鉴权是本机级的**。HttpOnly 会话 cookie，`Secure` 故意没设（本机 `http://127.0.0.1` 设了浏览器不回传，登录会死循环），上线必须挂 TLS 并打开。没有 OAuth/LDAP 单点登录，没有口令复杂度校验，没有登录失败锁定。
8. **容器化配置未实测**。本机没装 Docker，`docker-compose.yml` 与两个 Dockerfile 是按镜像构建逻辑写的；`start.ps1` 那条路是实测过的。
