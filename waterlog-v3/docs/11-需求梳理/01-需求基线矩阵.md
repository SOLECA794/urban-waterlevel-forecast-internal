## 0. 这份文档回答什么

`docs/06` 已给出「✅7 / ◐12 / ⬚4」的总数与单条现状，但它是一份**接口**文档——按接口组织，不是按业务条款组织。本文件换一个组织方式：**逐条对着 23 个条款问三件事**。

1. **基线要什么**（原文要求，不改写、不概括掉关键限定词）
2. **现在有什么**（可指到文件与函数的证据，不写「基本支持」这类无法证伪的话）
3. **差什么**（缺口要能被一项工作关掉，不写「进一步完善」）

这三栏合起来才是可核对的矩阵：任一条的「差什么」如果关不掉，招标应答时就不该写成「已满足」。

### 判定口径

| 记号 | 含义 | 判据 |
|---|---|---|
| ✅ | 已实现 | 有可运行代码路径 + 有实测证据 |
| ◐ | 部分实现 | 主链路通，但条款里的某个限定词（多源、动态、关联、追溯…）没落地 |
| ⬚ | 未实现 | 只有占位字段或完全不存在 |

**◐ 是最危险的一档**：功能看起来有，但它答的不是条款问的那件事。例如 8-4 要求用**实时监测值**判定越限，v3 用的是**预测值**——两者都叫「超阈值」，含义不同。

---

## 1. 一句话结论

23 条中 **✅7 / ◐12 / ⬚4**，**无不可行项**。

但按**投入产出**看，缺口不是平均分布的：

- **⬚4 条里有 3 条（8-1、9-3、10-6）指向同一件事**——v3 现在是一套「表格型树模型 + 确定性规则」的系统，条款基线描述的是一套「多模态基础大模型驱动的 AI 平台」。这不是补几个接口能弥合的，是**平台定位差异**。
- **◐12 条里多数是同一种病**——功能建在**仿真世界**里，条款要求它建在**真实数据源**上：真实气象预报（9-1/9-6）、视频图像（10-1/10-5）、平台台账（8-2/8-5）。
- **真正「只差工程量、不缺能力」的只有 4 条**：8-3 动态阈值、10-4 模型仓库、10-7 算力台账、9-9 运行台账。

第 3 节给出按这个判断排出的补齐顺序。

## 2. 23 条矩阵

### 模块 8 · 预警功能配置（6 条）

#### 8-1 雨情场景识别与适配 — ⬚

| 栏 | 内容 |
|---|---|
| **基线要什么** | 识别晴天/小雨/中雨/强降雨等雨情场景，**建立场景与点位预警规则的对应关系** |
| **现在有什么** | **没有场景模型**。对外网关的 `rainScene` 字段是占位——`api/internal/httpapi/aiwater.go:408` 原话：「v3 没有雨情场景模型（条款 8-1 明确是留白）」，三处结构体（`:411`、`:537`、`:687`）与过滤器（`:729`）全部固定返回 `unspecified` |
| **差什么** | ① 场景判定的输入与分级口径（按当前雨强？按预报累积？按持续时间？）；② 场景→阈值规则的关联表（哪些点位在强降雨档切换哪套阈值）；③ `rainScene` 由占位改为真实取值 |

**说明**：`docs/09-AI平台自研网关落地说明.md` 已记录「**不编枚举值**」的处置——这是对的，在场景口径与对方确认前不应发明枚举。但这也意味着 A-2/A-4/A-9 三个接口的 `rainScene` 字段目前是**结构性空转**。

#### 8-2 预警阈值分级配置 — ◐

| 栏 | 内容 |
|---|---|
| **基线要什么** | 面向道路易涝点/窨井液位/管网流量等对象，配置**设备、监测指标、雨情场景差异化**的阈值；支持等级、启停、适用点位、生效条件的统一管理 |
| **现在有什么** | 四级阈值存在且分级可用——`engine/waterlog/config.py` 的 `Site.thresholds` 是四元组（蓝/黄/橙/红，相对基准高程的积水深度 m），十站各有一套；`docs/09` 记录了四级→三级的对外映射（blue→low / yellow→medium / orange·red→high） |
| **差什么** | ① **阈值写死在 `config.py` 里**，改阈值要动代码并重训（ADR-0006 记录了原因）；② **只有一种对象**（道路积水点），没有窨井液位/管网流量两类对象；③ **没有「雨情场景差异化」这一维**（依赖 8-1）；④ 缺启停/生效条件字段 |

#### 8-3 动态阈值自动调整 — ◐

| 栏 | 内容 |
|---|---|
| **基线要什么** | 按雨情**自动匹配切换**阈值，并支持阈值查询/调整/保存 |
| **现在有什么** | 阈值查询有（`GET /api/rules` 与网关 A-4）；三因子规则可以在线预演与落盘（`POST /api/rules/preview` 用**同一条已发布曲线重判** before/after，不改模型——这是为「分清变化来自规则还是模型噪声」专门做的设计）；实测 `red 0.78→0.60` 导致 4 站升级、四级全 0.90+ 导致 10 站降级 |
| **差什么** | **「自动」这一半没做**。现在是人改规则→预演→保存，链路完整但触发者是人；条款要求的是按雨情场景自动切换（依赖 8-1 的场景模型）。规则版本可追溯，但**阈值调整日志**（谁在什么场景下把哪个点位切到哪一套）没有独立留存 |

#### 8-4 监测数据规则判定 — ◐

| 栏 | 内容 |
|---|---|
| **基线要什么** | 基于**实时值 + 监测状态 + 历史变化**判定，并**区分短时异常波动 / 连续越限 / 重复报警** |
| **现在有什么** | 三因子研判完整：`engine/waterlog/domain/rules.py` 的 `assess()` 用 `0.45·peak + 0.35·duration + 0.20·trend`，门槛 0.22/0.40/0.60/0.78，两道硬约束只降不升；超阈区间有 `thresholdSegments` 切分（前端 `EpisodeTimeline` 用） |
| **差什么** | ① **判定输入是预测值不是实时监测值**——`assess_from_forecast()` 把当前水位与未来预测序列拼起来算，这是「预测角度」的超阈，条款问的是「实测角度」的越限；② **没有「短时异常波动」与「重复报警」的区分逻辑**——三因子只看峰值/持续/趋势，不识别同一事件被反复上报；③ 监测状态（在线/离线/劣化）只作为降频信号（`agent.py` 的 `quality`），不参与判定 |

**这是最重要的一条 ◐**：非技术人员对照界面看「有超阈判定」，答辩时若被问「你们判定的是实测还是预测」，现有实现给不出条款要的答案。

#### 8-5 分级告警与信息关联 — ◐

| 栏 | 内容 |
|---|---|
| **基线要什么** | 关联点位/设备名/指标/实时值/雨情场景/适用阈值/发生时间，形成**可查询**预警记录，并**向既有监测预警业务模块提供规则判定结果** |
| **现在有什么** | 告警记录完整：四态（`ACTIVE_UNACK` / `ACTIVE_ACK` / `CLEARED_ACK` / `CLEARED_UNACK`）＋处置五态（open/dispatched/onsite/resolved/false_alarm）两轴分离；`GET /api/alerts` 可查、`/api/alerts/{id}` 可下钻、支持 ack/assign/disposition/notes；对外网关 A-3 `/warning/records` 与 A-20 `/warning/dispatch` 已定义 |
| **差什么** | ① 关联字段缺 **`rainScene`**（依赖 8-1）与 **`appliedThreshold`**（「本次用的是哪一套阈值」——规则可改，事后必须能答出当时按哪套判的）；② 「向既有监测预警业务模块提供判定结果」的**主动回传通道 A-20 未落地**（`docs/09` §5.2 已如实记录） |

#### 8-6 规则维护与运行追溯 — ✅

| 栏 | 内容 |
|---|---|
| **基线要什么** | 规则配置/修改/启停/执行记录查询，保留**阈值调整与预警触发日志** |
| **现在有什么** | `docs/06` §5 判为已实现。规则可查（`GET /api/rules`）、可改（`PUT /api/rules`，admin）、改前可预演（`POST /api/rules/preview`）；审计中间件记录写操作（`Audit` 挂在 `Authenticate` 内层，靠 `identitySlotKey` 让内层回填身份——这是修过的一个真 bug）；预警触发有完整事件流（SSE `/api/events`） |
| **差什么** | 无阻断项。**唯一加强项**：8-3 落地后，阈值自动切换需要一条独立于通用审计的「阈值调整日志」（谁/何时/何场景/从哪套切到哪套），目前可复用审计表但字段不够 |

### 模块 10 · 模型应用与调配（8 条）

## 4. 必须先说清楚的一件事：9-3 与 10-6 不是开发任务

`水涝监测软件部分.xlsx` 的模块 9/10 总述写了「依托内涝水位 AI 预测工作站内置的**多模态基础大模型**」，可行性分析里 9-3 与 10-6 的落地要点分别是「需在 AI 预测工作站侧提供统一模型服务网关」和「需明确外网出口与数据安全策略」，10-1 写着「视频侧依赖取流解码与录像下载能力」。

**这三句话合起来说明：条款假定的算力与模型底座不在本平台里，在对方的「AI 预测工作站 / 多模态预警一体机」上。**

那么现在的实现在这个前提下的定位是清楚的：

- v3 现在的能力（数值时序预测 + 确定性三因子研判 + 可解释调度）是**这个平台的时序侧引擎**，是真实、可验收、有实测证据的
- 条款里的「多模态协同」「大模型问答」要求它**接入**而不是**自研**一个基础大模型
- 因此 9-3/10-6 的正确处置是：**先把接入契约（A-18 `/llm/chat`、A-12 `/feature/dataset`、A-17 `/inference/tasks`）定义并落地成可切换的适配层**，让「有没有模型可用」变成配置项，而不是等模型到位再开发

**不要做的事**：不要为了凑条款而声称现有能力等于多模态协同。`docs/09` 已经记录过这个教训——「v3 的智能体是调度决策器不是对话机器人」，拿它应答 10-6 会在答辩现场被问穿。
