# ADR-0004：预警的「四态」与「处置」是两条独立的轴

- 状态：已采纳
- 日期：2026-10-21
- 影响面：`api/internal/domain/warning.go`、`api/internal/domain/alert.go`、预警中心页面

## 背景

预警事件天然有两组状态，很容易被误当成一组：

- **这条预警还成立吗？** —— 完全由模型决定。水位涨到阈值以上 → 触发；退到阈值以下 → 解除。值班员无法「让水位退下去」，也无法「让预警消失」。
- **我们对它做了什么？** —— 完全由人决定。派单给谁、有没有人到现场、是不是误报、泵站开没开。

如果合并成一个状态机（比如 `ACTIVE → DISPATCHED → RESOLVED`），会立刻出现无法表达的合法状态：**预警已经被模型解除（CLEARED），但现场还在排水（dispatched）**。值班员要么被迫提前关掉处置记录（丢掉现场信息），要么被迫把已解除的预警留在活跃列表里（污染一张图）。

## 决策

两条轴分开存，分开演进，互不覆盖：

**阅读轴（四态，模型驱动）**

```
ACTIVE_UNACK ──ack──> ACTIVE_ACK ──自动解除──> CLEARED_ACK
      │                                            ▲
      └────────────自动解除────────────────────────┘
                   CLEARED_UNACK
```

- 迁移只能由 `SyncWarning()` 触发（比较本轮研判与库中最新事件），或由 `AckWarning()` 触发（人工确认）。
- 非法迁移一律 **409 + 原话**：`已确认，无需重复确认`。不静默成功，也不改写状态。
- `ACTIVE_* → CLEARED_*` 时记 `cleared_at`；`ack` 时记 `acked_at`。

**处置轴（五态，人驱动）**

```
open ──> dispatched ──> onsite ──> resolved
  │            │            │           │
  │            └────────────┴──────────>false_alarm
  │                                       │
  └───────────────────────────────────────┘（resolved/false_alarm 可回到 open 重开）
```

- `dispatched → open` **故意不允许**：已经派出去的人不能假装没派过。要纠正就前进到 `false_alarm` 并写备注，留下痕迹。
- 非法迁移同样 409 + 原话：`不能从「已处置」直接改为「误报归档」`；同态重复：`已经是「已到场」，无需重复操作`。
- 每次迁移自动写一条 `alert_note`（`kind=status`），派单写 `kind=dispatch`，人工备注写 `kind=note`。备注不可编辑、不可删除 —— 它是处置过程的账本。

## 后果

- 一张图、预警中心只按阅读轴过滤（`active_only`），处置状态作为附加列展示。**活跃列表里可以出现「已派单且已到场」的事件，这正确**。
- 四态机可以完全自动跑（模型每 60 秒推一轮），处置轴只能靠人推进。两条轴的时间常数完全不同（分钟级 vs 小时级），分开后各自都不用为对方让步。
- 代价：前端要同时渲染两条轴，UI 上必须明确区分「预警状态」（只读，带脉冲点）与「处置状态」（可点，带按钮）。这一点在 `AlertsPage` 里用两个独立的卡片区块实现，标题分别写「预警状态」和「处置」。

## 被否掉的方案

**用一个七态机**（`ACTIVE_UNACK → ACTIVE_DISPATCHED → ... → CLEARED_RESOLVED`）：状态数爆炸（4×5=20 种组合，其中大部分无意义），且每加一个处置动作都要改状态机、改迁移表、改前端。两条轴的笛卡尔积本来就该由两个字段表达。
