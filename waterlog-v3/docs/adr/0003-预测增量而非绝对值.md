# ADR-0003：模型预测「水位增量」，不预测「绝对水位」

- 状态：已采纳
- 日期：2026-10-21
- 影响面：`engine/waterlog/ml`、`engine/waterlog/service/forecast.py`、滚动修正

## 背景

水位预测有两种建模方式：

- **A. 直接回归绝对值**：输入历史水位 + 降雨 + 站点属性，输出「3 小时后水位是 7.85 米」。
- **B. 回归增量**：输出「3 小时后水位比现在高 0.03 米」，再用当前实测加上去。

直觉上 A 更直接，但在这个场景里它是错的。

## 理由

**1. 站点之间的高程差会主导损失函数。**
10 个站点的基准水位从 3.6 米到 16.3 米不等（隧道底、桥下涵洞、江边泵站天然差十几米）。用绝对值做目标，RMSE 里绝大部分误差来自「这个站本来就在 16 米」，而不是「这个站会不会淹」。模型会花容量去学每个站的常数偏移 —— 那是查表就能做到的事。

**2. 增量天然以观测为锚，曲线不会和实测断裂。**
绝对值的模型在起点就可能偏离实测 5 厘米，画出来是预测曲线从空中开始。增量模型在 `t=0` 处严格等于实测，曲线和实测点必然连上。**这一条直接决定了趋势图可不可信** —— 值班员第一眼看的是「预测线是不是从我脚下这条线接出去的」。

**3. 增量更平稳，残差更接近同分布。**
绝对值在暴雨期会剧烈抬升，分布严重右偏；增量在 90% 的时间里接近 0。平稳目标让梯度提升的树分裂更有意义，也让置信区间的 σ 估计（分站点分预见期）更站得住。

## 决策

- `features.build_target()` 返回 `level[o+h] - level[o]`（增量）。
- 训练目标、验证目标、持久化基线全部用增量。
- **融合对象是「持久化基线」（Δy = 0）而不是线性外推**。理由：线性外推在退水期会一路外推到负值（实测 12h 预见期 skill = −3.27），它没资格当融合对象。权重 `w` 于是有明确语义：**对该站点该预见期，模型相对「水位不变」这个零假设的信任度**。实测 60/180/360 分钟全是 1.0，720 分钟有 6 个站点降到 0.6~0.95 —— 长预见期自动保守化，符合设计意图。
- 发布时 `yhat = now_level + Δy_hat + 修正量`，再由物理约束钳制到 `[base_level, base_level + 1.5]`。

## 后果

- 站点间指标可比：60 分钟 blend RMSE 0.009 米、NSE 0.753、相对持久化 skill +0.503，四个预见期都稳定在 0.63~0.78 的 NSE。
- **必须单报「事件样本」指标**。全样本里 90% 是平静水面（Δy≈0），持久化基线在那里几乎零误差，混合平均会把模型的价值抹平。所以额外统计「预见期末水深 ≥ 蓝色阈值」的样本（n=3161）：blend 的 event_skill 是 +0.700/+0.536/+0.491/+0.297，而线性外推是 +0.281/−0.279/−0.583/−0.131 —— **线性外推在真正要紧的样本上比「什么都不预测」还差**。这才是「模型有没有用」的答案。
- 代价：增量模型无法预测「站点从干到湿」的启动过程（因为起点是 0 增量，需要靠降雨特征推）。实测这一档由 `fc_3h`、`fc_excess_3h`、`saturation` 三个特征承担，置换重要性 top3 正好是它们。

## 关联事故

**量纲混用 +7.85 米。** `warmup_corrector` 里 `_predict()` 返回增量，却被直接当成绝对水位去和 `ds.level[o+hstep]` 相减，误差均值算成 +7.85 米（≈ S01 的基准高程）。修正器于是每轮加 3.2 米，把 S01 顶到物理上限、预警直接判红。

修法是一行 `yhat = ds.level[o, sites] + self._predict(...)`，但真正的防线是后来加的两道：

1. 修正量钳制 `applied = clip(applied, -3σ, +3σ)` —— 修正器再出问题也不允许把曲线推出置信带。
2. 前端 `domain/units.ts` 把 `Meters`（绝对水位）和 `Delta`（增量）做成品牌类型，`depthOf(level, base)` 是唯一允许换算的函数。混用在 `tsc` 阶段就报错。

**教训：当一个 bug 的数值恰好等于某个物理常量（这里是站点高程）时，先怀疑量纲，而不是怀疑算法。**
