# ADR-0005：前端分五层，页面只做布局

- 状态：已采纳
- 日期：2026-10-21
- 影响面：`web/src/**`

## 背景

第一版前端的实际结构是「一个页面一个文件」：`OverviewPage.tsx` 474 行、`ModelPage.tsx` 553 行。`pages/` 一个目录占了 94% 的代码量。

每个页面文件里同时住着五种东西：

1. **取数**（`useQuery` 调用与轮询间隔）
2. **换算**（`p.yhat - p.base_level` 算积水深、`thresholds[3]` 取红阈值）
3. **派生**（排序、取 top5、按小时归并）
4. **布局**（grid 比例、sticky、响应式断点）
5. **展示**（某个数字该用几位小数、该什么颜色）

五种东西的**修改理由完全不同**：接口加字段、阈值口径变化、值班员想换排序、视觉改版 —— 但它们在同一个文件里，改任何一样都要重读 500 行。

这不是风格问题，它已经产出过真实 bug：

- `OverviewPage.tsx:149` 用后端算好的 `s.depth`，`ModelPage.tsx:240` 前端自己算 `p.yhat - p.base_level`。**同一个物理量两处算，口径迟早分叉。**
- `thresholds` 是 `number[]`，三处按位置访问并各自硬编码兜底 `|| 0.46`。0.46 是 S01 的红阈值，套到 S08（13.06 米基准、红阈值 0.561）就是错的。**魔法索引 + 魔法常量，静默错误。**
- 「合计积水」把 10 个站点的水深相加显示 3.21 米。各站是独立汇水单元，深度不可相加 —— 这是**量纲没错但物理错了**。

## 决策

分五层，依赖单向向下：

```
pages/       布局与装配。允许 useXxx() 取数据、允许 .map() 渲染。不允许 fetch、不允许换算、不允许排序。
  ↓
view/        视图模型。把领域数据变成「这一屏需要什么」。useSituation / useWatchlist / useMapPoints / useSiteEvidence / useTrust。
  ↓
components/  primitives（无领域知识）+ domain（有领域知识）+ charts
  ↓
domain/      纯函数与品牌类型。无 React、无 fetch、无 IO。units / time / level / site / reading / assessment / forecast / rules / metrics / series / system
  ↓
data/        dto（线上形状）+ adapters（唯一换算点）+ client + queries + live（SSE 单例）
```

四条硬规则：

**1. 换算只允许发生在 `data/adapters.ts`。**
DTO 是「后端长什么样」，domain 是「业务上是什么」。`picp90` 引擎给百分数（92.36）前端要比例（0.9236），这个 `/100` 只出现在 `adaptMetricRow` 一处，并带注释说明为什么。线上契约变了只改 adapter，页面不动。

**2. 阈值必须具名。**
`domain/site.ts` 的 `Thresholds{blue,yellow,orange,red}`，`thresholdOf(t, level)` 是唯一访问路径。`adaptThresholds` 不足 4 级时**抛 `ContractError` 而不是兜底** —— 兜底会把契约错误变成静默的错数字。

**3. 物理量是品牌类型。**
`Meters`（绝对水位）/ `Depth`（积水深）/ `Delta`（增量）/ `Rate`（变化率）/ `RainRate` / `RainSum` 六个互不兼容的类型，构造函数是唯一入口，`depthOf(level, base)` 是唯一换算函数。混用在 `tsc` 阶段就报错。这一条直接来自「+7.85 米」和「合计积水 3.21 米」两次事故。

**4. 数据视图按屏分层，不要一个 God DTO。**
一张图首页需要四种粒度，各有各的字段集：

| 层 | 类型 | 条数 | 回答什么 | 不需要的字段 |
|---|---|---|---|---|
| L1 结论 | `SituationSummary` | 1 | 现在整体怎么样 | 每站的水深、曲线 |
| L2 空间 | `MapPoint[]` | 10 | 在哪里 | 研判依据全文、置信区间 |
| L3 明细 | `SiteGlance[]` | 10 | 多深、多急 | 决策 signals、历史序列 |
| L4 溯源 | `SiteEvidence` | 1/站 | 凭什么这么判 | 其它 9 个站 |

原来的 `OverviewSite` 是 20 字段的 God DTO，五类关注点（静态属性 / 实时遥测 / 派生量 / 预警研判）挤在一起，`warn_level`（枚举）和 `level`（米）并列。拆开后每个 hook 只挑自己要的字段，加字段不会牵动四个页面。

**5. 排序这类派生放 view 层。**
`useWatchlist(sort)` 一个函数，一张图和站点列表共用。之前两处各写一遍排序，已经出现过不一致（关注清单按分数、站点表按等级）。

## 后果

- `pages/` 从 2456 行降到约 1500 行，且每个文件读起来是一段布局而不是五段逻辑。
- 新增 `domain/`（14 文件 1169 行）、`view/`（5 文件 436 行）、`data/`（5 文件）。总行数变多了 —— 这是分层必然的代价，换来的是**每行的修改理由唯一**。
- 品牌类型让页面代码变啰嗦（`DepthValue` 只吃 `Depth`，得先 `depthOf()`）。但它在编译期挡掉了两次已发生事故的同类问题。
- 一个具体的收益：`FreshnessBadge` 与 `TrustBanner` 做出来后，「数据滞后」第一次有了视觉表达。之前 `quality<0.7`、预测过期、SSE 断连三种情况在 UI 上和正常无区别。

## 教训

**「信息太多」往往不是信息的问题，是分类的问题。** 用户反馈「信息量过于冗余」时，正确的动作不是删字段，而是问：这个字段属于哪一层？L1 需要它吗？不需要就下移到 L3/L4，同一屏的信息量自然降下来。
