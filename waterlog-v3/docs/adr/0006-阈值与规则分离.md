# ADR-0006：可配置的是规则，不是阈值本身

- 状态：已采纳
- 日期：2026-10-21
- 影响面：`engine/waterlog/domain/rules.py`、`engine/waterlog/infra/rules_store.py`、规则配置页

## 背景

老师的要求里有一条：「预警等级与阈值必须可配置」。这句话有两种读法：

- **A. 每个站点的四级阈值可改**（蓝 0.06 / 黄 0.18 / 橙 0.30 / 红 0.46 这些数）。
- **B. 三因子怎么合成等级可改**（权重、分档、最短持续、趋势跨档）。

两者都要，但**性质完全不同**，混在一起设计会出问题。

阈值是**业务标定值**：它由「这个下穿隧道多深会断行」这种现场事实决定，改它等于重新定义「什么叫做淹」。规则是**研判策略**：它由「我们更怕漏报还是更怕误报」这种管理偏好决定，改它不影响「什么叫做淹」，只影响「什么情况值得惊动人」。

## 决策

**阈值：属于站点，跟站点走，不跟规则走。**

`config.py` 的 `Site.thresholds` 是一个 4 元组，写死在站点定义里。改它需要改代码 + 重新训练（因为特征工程里有 `thr_blue/yellow/orange/red`、`headroom_red`、`saturation` 这些派生特征）。

**规则：独立文档，热更新，有版本，可预演。**

`engine/data/rules.json` 存一个 `Rules` 文档：

```json
{
  "weights":            { "peak": 0.45, "duration": 0.35, "trend": 0.20 },
  "score_cutoffs":      { "blue": 0.22, "yellow": 0.40, "orange": 0.60, "red": 0.78 },
  "min_duration_min":   { "blue": 20, "yellow": 30, "orange": 45, "red": 60 },
  "duration_saturation_min": 180,
  "trend_upgrade_slope":    0.25,
  "trend_downgrade_slope": -0.15,
  "trend_score_span": 0.5,
  "horizon_min": 180,
  "min_level_for_alarm": 1
}
```

`load_rules()` 与 `DEFAULT_RULES` 做**深合并**（不是整块替换）—— 否则旧文件缺一个新加的键就会 KeyError，或者更糟：`weights` 只给了 `peak` 就把另外两个因子静默清零。`merge_rules(base, patch)` 对 `weights`/`min_duration_min`/`score_cutoffs` 三个子字典逐键合并。

## 三条不可配置的红线

规则可以改，但下面三件事写死在代码里：

**1. 两道硬约束只降不升。**
- 持续时间未达 `min_duration_min[level]` → 封顶降级。
- `min_level_for_alarm` 之下 → 直接 `none`。

它们**只能把等级往下压，不能往上抬**。理由：这两条是「防误报」的闸门。如果允许它们抬升等级，改一个参数就能让全站报红，而改参数的人未必意识到自己在制造噪声。

**2. 三因子权重必须和为 1。**
`validateRules()` 检查 `|sum - 1| < 1e-6`，不满足时保存按钮禁用并给出原因。理由：权重和不为 1 时综合分的量纲就漂了，而 `score_cutoffs` 是按「和为 1」标定的 —— 0.78 这个红警分档在权重和 0.8 时对应完全不同的物理含义。

**3. 分档阈值必须严格递增，最短持续必须非递减。**
`blue < yellow < orange < red`、`min_duration_min` 逐级不减。否则会出现「分数 0.5 判红、0.8 判蓝」这种自相矛盾的配置。

## 规则影响预演（`POST /rules/preview`）

改规则前必须先看到「改了会发生什么」。实现要点：

- **不重新预测**。用**同一条已发布的曲线**（`ForecastService.last_series` 里缓存的 5 分钟分辨率序列）重判 before/after。理由：重新预测的话，变化里混着模型噪声，分不清是规则改的还是这一轮雨变了。
- 返回逐站点 `{before_level, after_level, before_score, after_score, before_reason, after_reason, direction}` + 汇总 `{upgraded, downgraded, unchanged, total}`。
- 排序按 `direction == "same"` 在后、`|Δscore|` 降序 —— 值班员先看动了的那几个。
- 尚无预测结果时返回 **409「尚无预测结果，无法预演」**，而不是空列表（空列表会被读成「改了没影响」）。

## 后果

- 规则改动是**秒级生效**的（PUT 后引擎内存里的 rules 换掉，下一轮研判即用新规则），不需要重训。
- 阈值改动是**小时级**的（改代码 + 重训 90 秒 + 重启）。这是刻意的：阈值变更是标定变更，值得走一次完整验证。
- `min_level_for_alarm` 的语义是**等级序**（1=蓝 2=黄 3=橙 4=红），不是 0~1 的分值。这个字段曾经在前端被当成「最低综合分」渲染成 0~1 的输入框，读起来像「0.22 分才报警」。已修正为四按钮等级选择器 —— **一个字段的语义如果两种读法都说得通，就必须在 UI 上消歧，不能靠注释。**
