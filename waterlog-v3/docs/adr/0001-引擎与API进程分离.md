# ADR-0001：预测引擎与业务 API 分成两个进程

- 状态：已采纳
- 日期：2026-10-21
- 影响面：整体架构、部署形态、故障模式

## 背景

这个系统有两件性质完全不同的事：

1. **算**：把 47 维特征喂给 4 个预见期的梯度提升模型，做滚动修正，跑三因子研判。CPU 密集、依赖 numpy/pandas/scikit-learn、有几百 MB 的模型常驻内存、一次训练要 90 秒。
2. **服务**：接遥测、存 SQLite、维护预警四态机、推 SSE、托管前端。IO 密集、要低延迟、要能水平扩。

如果把两件事放进一个进程（比如全 Python，或者用 Go 重写模型推理），会立刻撞上三个具体问题：

- **训练会阻塞请求**。Python 的 GIL 加上 scikit-learn 的单线程热点，一次重训 90 秒期间整个 API 不可用 —— 而重训恰恰发生在「值班员觉得模型不准」的时候，也就是最不能不可用的时候。
- **依赖互相绑架**。给前端加一个分页参数不应该要求重新拉 200MB 的 scikit-learn 镜像；反过来，换模型库也不应该影响 API 的稳定性。
- **故障域不同**。模型服务挂了，遥测还能收、预警还能按上一次的预测维持、历史还能查 —— 这些都不需要引擎在线。合成一个进程就把「模型挂了」升级成「整个系统挂了」。

## 决策

拆成两个进程，用 HTTP + JSON 通信：

- `engine`（Python/FastAPI，:8201）：只算。特征工程、训练、预测、修正、研判、模拟器。**不对外暴露**。
- `api`（Go/chi，:8200）：只服务。持久化、状态机、SSE、静态托管、鉴权、审计。它是唯一的对外入口。

数据流是**双向**的：

```
engine --POST /api/ingest/telemetry--> api     （仿真推进出来的实测）
engine --POST /api/ingest/forecast---> api     （每 60 秒一轮的预测 + 研判）
api    --GET  /forecast, /sites------> engine  （启动拉站点元数据；反代 /metrics 等只读视图）
```

引擎是**推**的一方，因为它掌握仿真时钟；API 是**拉**的一方，只在启动和用户点重训时发起请求。

## 后果

**好处**

- 训练期间 API 完全可用，只是 `/api/health` 的 `engine_ok` 变 false、预测不更新。前端已经把这个状态渲染成「预测滞后」而不是空白页。
- 两侧可以独立升级、独立重启。改前端不用动引擎，改模型不用动 API。
- 故障可观测：`engine_ok` 是一个明确的一等状态，不是一个被吞掉的异常。

**代价**

- **时间一致性变成分布式问题**。这是实际踩到的坑：模拟器 60 倍速，仿真时间跑在墙钟前面，引擎和 API 各自持有时间概念，重启后 `MAX(telemetry.ts)` 卡在旧未来值、新预测 `issued_at` 比旧快照小、API 按 `issued_at DESC` 取到旧预测 —— 一张图定格。解法见 ADR-0002。
- **契约漂移**。两侧各有一套结构体定义，字段名不一致时不会编译报错。实际踩到两次：前端按 `/api/models` 请求而后端是 `/api/models/versions`（404 静默）；PICP90 引擎给百分数前端当比例乘了 100（显示 9236%）。缓解手段是前端 `data/dto.ts` 与 `data/adapters.ts` 把线上形状和领域模型隔开，换算只允许发生在 adapter 一处。
- **多一跳延迟**。反代 `/metrics` 这类只读视图时多一次本地 HTTP 往返，实测 <2ms，可接受。

## 被否掉的方案

- **全 Python 单进程**：训练阻塞请求，不可接受。
- **Go 重写模型推理**：梯度提升的推理逻辑要自己实现或绑 CGO 到 libxgboost，收益是省一个进程，代价是训练链路（scikit-learn 的交叉验证、置换重要性、分位数标定）要重写一遍。不划算。
- **消息队列解耦**（Kafka/Redis Stream）：这个规模（10 站点、5 秒一个 tick、每分钟一轮预测）用不上，引入的是运维成本而不是能力。HTTP 直推足够，且失败可见。
