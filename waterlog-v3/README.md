# waterlog-v3 · 城市内涝水位预测预警系统

一套**算法链路真实可跑**的城市内涝预测预警系统：多源数据融合 → 多预见期趋势预测 →
三因子联合研判 → 多源协同滚动修正 → 预测与实际对比评估 → 模型校准。
数据由内置水文模拟器生成（可注入暴雨、可回放），但**从数据到预警的每一步都是真算的**。

```
┌──────────────────────────────────────────────────────────────────────┐
│  Python 引擎 :8201                     Go API :8200         React 前端 │
│  ┌────────────────────────┐          ┌──────────────┐    ┌───────────┐│
│  │ 水文模拟器（60x 加速）  │  遥测    │ 遥测入库      │SSE │ 一张图     ││
│  │ 特征工程（47 维）       │ ───────► │ 预警四态机    │───►│ 站点详情   ││
│  │ 4×梯度提升树（1/3/6/12h）│  预测    │ 快照存储      │    │ 预警中心   ││
│  │ 三因子研判 + 滚动修正   │ ───────► │ 静态托管 SPA  │    │ 模型评估   ││
│  └────────────────────────┘          └──────────────┘    │ 规则配置   ││

└──────────────────────────────────────────────────────────────────────┘
```

## 一键启动

```powershell
cd waterlog-v3
.\start.ps1
```

首次运行会自动：生成 60 天模拟历史 → 训练 4 个预见期的模型（约 90 秒）→ 构建前端 →
编译 Go API → 启动引擎与 API → 等首轮预测推送完成。

打开 <http://127.0.0.1:8200> 即可。

| 参数 | 作用 |
|---|---|
| `-SkipBuild` | 跳过前端构建（`web/dist` 已是最新时用） |
| `-Reset` | 删除数据集/模型/评估库，全部重建 |
| `-Stop` | 停止引擎与 API |
| `-ApiPort` / `-EnginePort` | 换端口（默认 8200 / 8201） |

依赖：Python 3.11+（numpy / pandas / scikit-learn / fastapi / uvicorn）、Go 1.22+、Node 18+、Chrome（仅截图脚本需要）。

## 系统在做什么

### 1. 多源数据融合

模拟器按双面积水库模型生成 10 个站点的水文过程：`产流 = 雨强 × 不透水率 × 汇水面积`，
`排水 = 管网能力 × 汇水面积 × 效率 × (1 - 顶托系数)`，`溢流 = k·h^1.5`，
水深超过漫溢高度后**有效水面自动拓宽**（这是把峰值压在物理合理区间 0.6~0.8m 的关键约束）。

每个 5 分钟步长同时产出四路数据，全部进入特征工程：

| 数据源 | 内容 | 特征 |
|---|---|---|
| 实时监测 | 水位（含传感器噪声与 1.2% 劣化概率）、雨量 | `level_lag*`、`d_level_*`、`slope_1h`、`rain_now`、`rain_sum_*` |
| 历史降雨 | 60 天累计雨量、过程线形态 | `rain_sum_30m/60m/180m/360m/720m/1440m` |
| 历史积水 | 水位极值、波动幅度、加速度 | `level_max/min/range_3h`、`accel` |
| 气象预报 | 1h/3h/6h/12h 预报雨量（带系统性低估与随机误差） | `fc_1h/3h/6h/12h`、`fc_excess_3h/6h` |
| 站点属性 | 汇水面积、积水面积、不透水率、管网能力、基准水位、四级阈值 | `impervious`、`drain_rate`、`pond_ratio`、`thr_*`、`headroom_red`、`saturation` |
| 时间上下文 | 时刻、星期、月份 | 三角函数编码 |

共 **47 维**，在 `engine/app/features.py` 的 `FEATURE_NAMES` 里集中声明——
训练、推理、重要性分析全部按名字取列，不出现魔法列号。

### 2. 趋势预测（1h / 3h / 6h / 12h）

每个预见期一个 `HistGradientBoostingRegressor`，预测目标是**水位增量 Δy** 而不是绝对水位：

- 增量以实测为锚，预测曲线与实测曲线天然连续，不会在衔接处断裂；
- 增量更平稳，树模型更容易学到"雨强 → 涨多少"的关系；
- 反归一化就是 `yhat = 当前实测 + Δy`。

同时训练三个对照模型，在同一张表里对比（这是**证明模型有价值**的方式，不是自说自话）：

| 模型 | 定义 |
|---|---|
| 持久化基线 | 水位保持不变（Δy = 0），最笨的预测 |
| 线性外推 | 当前斜率 × 预见步数，最朴素的"预报员做法" |
| 梯度提升树 | 47 维特征 → Δy |
| **融合（上线）** | `w · 树模型 + (1-w) · 持久化基线`，w 按站点 × 预见期在验证集网格搜索 |

**为什么融合对象是持久化基线而不是线性外推**：线性外推在退水期会一路外推到负值，
拿它当融合对象等于给模型埋雷。权重 w < 1 表示该站点该预见期上树模型并不稳定优于基线，
系统自动保守化——这是设计意图，不是缺陷。

不确定性用分站点分预见期的残差标准差给 90% 区间（z = 1.6449），并做两件事：

- **区间钳制在物理约束内**：水位不低于基准高程、不超过 `base + 1.5m`；
- **修正量钳制在 ±3σ 内**：滚动修正器即使失效，也不允许把曲线推出置信带。

### 3. 三因子联合研判

预警等级不是"预测峰值过阈值就报警"，而是三个因子加权：

```
score = 0.45 · peak + 0.35 · duration + 0.20 · trend
```

| 因子 | 含义 | 归一化 |
|---|---|---|
| peak | 研判窗口内预测峰值 / 该级阈值 | 分段映射到 0~1.5 |
| duration | 预测超过阈值的持续时间 / 饱和时长 | 线性到 1 |
| trend | 预测窗口内的水位变化斜率 | 映射到 0~1 |

再按 `score_cutoffs`（0.22 / 0.40 / 0.60 / 0.78）分到蓝/黄/橙/红。
两道硬约束会**降级**而不是升级：

- 超阈持续时间不足 `min_duration_min[level]` 时，等级封顶；
- 趋势斜率 ≥ +0.25 m/h 升一级、≤ -0.15 m/h 降一级（短时尖峰不等于持续内涝）。

所有参数都在 `engine/data/rules.json`，可在前端「规则配置」页热更新，保存即刻重算全部站点等级。

### 4. 多源协同滚动修正

`RollingCorrector` 按 (站点, 预见期) 维护两个指数加权统计量：系统性偏差均值 `err_mean`
与绝对误差 `err_abs`。每轮预测把新息按预见期衰减后叠加到模型输出上：

```
gain    = clip(1.6 · err_abs / 0.05 · 0.25, 0.05, 0.6) / (1 + h/360)
delta   = gain · err_mean · 1/(1 + h/240)
yhat    = clip(model_yhat + clip(delta, -3σ, 3σ), base, base + 1.5)
```

三个设计决定值得说明：

1. **新息取系统性偏差而非瞬时观测差**。用瞬时差会把传感器噪声直接灌进预测曲线，
   预测会跟着噪声抖。
2. **按预见期衰减**。12h 的预测本来就该有更大自由度，不该被 1h 的偏差强行拉齐。
3. **启动时离线回放 3 天预热**。否则刚启动的第一个小时修正强度是 0，等于白跑。

协同的第二个来源是**气象预报修正**：用无截距最小二乘回归出每个站点"雨量 → 水位"的弹性 β，
把预报雨量与实际雨量的差异折算成水位增量。

### 5. 预测 vs 实际对比与校准

每条预测在发布时落库（含发布时刻的实测水位作为持久化基线锚点），
到预见期走完后自动结算实际值。评估看板给三种口径：

| 口径 | 用途 |
|---|---|
| 离线 3 折交叉验证 | 训练时的整体精度（含 NSE、CRPS、PICP90、PINAW） |
| **事件样本**（预见期末水深达蓝阈） | 最该看的一列：平静时刻会稀释全样本指标 |
| 在线滚动（近 N 小时已结算） | 模型上线后到底准不准，用"水位不变"当分母 |

`skill = 1 − RMSE/RMSE_持久化基线`，> 0 表示比"水位不变"更准。

校准闭环：看在线 skill 掉 → 触发重训（前端按钮或 `POST /api/retrain`）→ 新模型版本热替换，
旧版本指标留档对比；规则不合理就改规则，不用改代码。

### 6. 智能体值班

每个预测周期对每个站点做一次调度决策（`engine/app/agent.py`）：
看雨强、预报雨量、水位斜率、传感器质量，决定这一轮是"主动加算"还是"常规"，
传感器劣化时自动降级到线性兜底。决策连同信号一起入库，前端「模型评估」页可查。

这是"智能体"在这个系统里的具体形态：**不是对话机器人，而是每一轮自己判断
"这个站点现在值不值得算、该怎么算、算出来能不能信"**。

### 部署时踩的两个真坑

1. **模型不能跨 scikit-learn 大版本加载**。本机训练用的 1.8.0，服务器 pip 装到 1.5.2，
   引擎起来就报 `ModuleNotFoundError: No module named '_loss'` —— joblib 反序列化要 import
   训练时那个私有模块。修法是把 `scikit-learn==1.8.0 numpy==2.3.5 joblib==1.5.3` 钉死在服务器上。
   **模型是 pickle，不是跨版本格式**，这条对以后升级同样成立。
2. **Go API 默认只听 `127.0.0.1`**（本机开发不需要对外，这是刻意的）。部署时新增了
   `WL_API_HOST`，默认值保持保守，只在 systemd 单元里设 `0.0.0.0`。

### 版面上不许有肉眼可见的空白

「卡片都很满」和「整屏没有空档」是两件事，要分两个工具量：

| 工具 | 量什么 | 什么时候用 |
|---|---|---|
| `scripts/measure-overflow.mjs` | **卡片内部**有没有被裁（`clientHeight` vs `scrollHeight`） | 每次改完面板内容 |
| `scripts/probe-gaps.mjs` | **栏与栏之间**有没有空洞（按 x 分栏、逐 y 算块间空隙与栏尾空隙） | 每次改完版面 |

三条纪律：

1. **先量再改。** 曾被一张缩略图骗过，以为「右侧留白」，量完发现三栏底边全部对齐；
   真正的问题是另一张卡里的图形只画了上半部。
2. **卡片高度由版面求解给，不许写死。** `Widget` 用
   `cloneElement(children, { style: { ...children.props.style, height: '100%' } })`
   注入高度 —— 面板自己的 `style` 在前、`100%` 在后，所以**面板里写的
   `style={{height:190}}` 通常赢不了**。但别指望这个顺序：`多类别对比` 那次
   就因为包装方式不同，写死值真的生效并溢出 22px，而 `tsc` 不报错。
   判据是 **实测值必须等于版面值**（`measure-overflow` 与 `board_layout.py verify`
   对得上），不是「我看代码里没写死」。
3. **空白的两种成因分开治。** 一种是「位置空着」（补组件或调权重），
   另一种是「组件在那儿但图形只画了上半部」（改画布 padding / `flex:'1 1 0'` 均分）。

## 大厅大屏

路由 `/board` 是**九页轮播**：第 1 页一屏看全，后 8 页各把第 1 页上的
一块图放大到整屏。每页 3 秒（第 1 页 5 秒），右上角 `?page=N` 可以定屏。
旧的三屏版本仍然可用，在 `/board/legacy`——它被值班台当常驻背景用，
两种用途不该互相迁就。

### 九页：一页只回答一个问题

| # | 页面 | 主角 | 一眼要读出来的事实 |
|---|---|---|---|
| 1 | 水位预测总览 | 地图 + 八块缩略 | 红色 0/10 站、当前最深 0.55 m、1 小时后 0.48 m、当前雨强 |
| 2 | 全城积水分布 | 地图气泡 | 哪几个街道在报警，气泡越大越深 |
| 3 | 十站水位预测 | 十条实测+预测曲线 | 谁最高、谁在退、红阈线横穿在什么高度 |
| 4 | 单站水位过程 | 最深站一条线 | 六小时前到现在涨了多少，什么时候越过红阈 |
| 5 | 四预见期落点 | 四个大字 + 四条短柱 | 1/3/6/12 小时后分别落到哪个水位 |
| 6 | 几点会翻红 | 一条 12 小时轴 + 十个滑块 | 哪些已经超了，哪些会在几点超 |
| 7 | 预报与实际 | 双线 + 平均误差 | 这套预测到底准不准 |
| 8 | 积水程度排行 | 十条横条 | 十站排第几、差多少 |
| 9 | 雨还在下吗 | 24 根雨量柱 | 雨峰在哪、现在还在下几点几 |

三条纪律（写进 `board/zoom/types.ts` 的文件头，评审逐条查）：

1. **图表只留四种**——地图气泡、折线、横条、柱状。这四种的长度/高度/直径
   都能随数据肉眼变化。雷达图、热力图、桑基图、构成环都被删掉了：它们
   好看，但「现在到底多深」这件事在它们上面读不出来。
2. **每页只有一个主角 + 3~5 个数字。** 第 5 页除了四个预见期，连「模型 blend、
   ±0.02」都只是灰字小注；页脚一行写「现在 0.52 · 红阈 0.46 · 最高 0.48」。
3. **动效必须跟着数据变**——曲线末端、柱高、条长、气泡直径、数字跳。
   缓慢自转、扫光、粒子这些与数据无关的装饰一律不要；`prefers-reduced-motion`
   下全部停。

### 放大页的空白只能靠求解，不能靠目测

第 6 页（翻红时刻）第一版行高写死 46px，10 行只占了上半截，下面 400 多像素空白；
第 8 页（排行）也是 10 行占 600px、上下各空 200px。改法都是同一句：
**行高由可用高度反算**——`Math.min(88, Math.max(46, floor((h - 轴高 - 页脚) / 行数)))`。
写死值的问题是它只在某一版数据下正确，而轮播大屏每天的数据都不一样。

### 一页里「置信带为零」是一种撒谎

深水四站曾出现「四档预见期完全相同、`upper-lower` 恒为 0、曲线是一条直线」。
根因不在图表，在引擎 `engine/waterlog/service/forecast.py` 的钳制：

- `cap = base + 1.5` 把预测钉死在 1.5 m 水深，而实测已经 2.7 m，
  `lo/hi` 一起被钳到同一点 ⇒ 带宽 0，等于告诉观众「我们知道得非常准」。
- 增量模型是在「最深 0.8 m」的数据上训的，遇到 2.7 m 是分布外，
  它外推出「1 小时退水 1.2 米」——而双面积水库实测退水只有 0.02~0.2 m/h。

修法三条：`cap` 改成动态（`base + max(1.5, depth_now*1.6 + 0.35)`）；
增量加物理速率包络（涨 ≤0.60、退 ≤0.22 m/h，按预见期缩放）；
钳制后保证 `hi - lo >= 0.004`。**带宽是模型对自己不确定性的承认，
不是可以为了好看而压成 0 的装饰。**

### 版面上不许有肉眼可见的空白

「页面不要留空白」这句话，落到工程上不是「把卡片撑大」，而是三件具体的事：

1. **先把空白量出来，再动手。** `scripts/measure-overflow.mjs` 只能查「有没有裁切」，
   查不出「卡片里画了一条线但下面空一半」——后者 CSS 层面 `clientHeight === scrollHeight`
   完全正常。所以当时另写了两个一次性 CDP 探针（逐块量内容实际占用高度 /
   按栏量块间与栏尾空隙），用完即删；要复现就照 `measure-overflow.mjs` 的写法
   把 `getBoundingClientRect` 换成分块量。**这一轮真正的空洞只有一个：右栏
   `836→964` 的 128px** —— `duration` 在 `layout.ts` 里有坐标，但 `BoardPage.tsx` 里
   根本没有对应的 `<Widget>`，位置就白占着。
2. **卡片高度由版面求解给，不许在面板上写死。** `多类别对比` 曾写
   `style={{ height: 190 }}`（那是旧版面的数值），它会在 `Widget` 把面板设成 `100%`
   之后**覆盖掉 100%**，容器只有 161px 而面板仍要 190px → 溢出 22px。
   现在这两个面板的高度完全由 `layout.ts` 控制。
3. **空白的两种成因要分开治。** 一种是「容器有高度、内容不占」——把行改成
   `flex: 1 1 0` 真正长高（`多预见期预测` 四行、`三因子研判` 三行都这么修，
   行内的阈值色带与因子进度条也顺势从 4px / 3px 加高到 10px / 8px）；
   另一种是「图形没铺满容器」——`水位与预测` 的 `<svg>` 缺 `preserveAspectRatio`，
   按宽度缩放后上下各留约 80px 黑边，补上 `none` 即解决。

### 层级靠版面，不靠给单张卡加装饰

要让某张卡「看起来最重要」，最省事的是给它加粗边框、换底色、加发光。
**但那是错的**：面板样式是全屏统一的一套参数，单独改一张就破坏了
「所有卡都在同一套视觉语言里」这条已经立住的原则，读者会以为它坏了。

真正的层级信号是**面积和位置**。「水位与预测」原来与邻居三等分（各 422px），
改成占中栏第三行的 38%（465px）之后，从 3 米外一眼就看得出它是主角，
而且没有引入任何新的视觉元素。

改宽度时必须让宽度**精确闭合**（三块 + 两个 GAP = 总宽），
所以先算再写、写完立刻用 `_tools/board_layout.py verify` 验。
本轮第一次改就写坏了：我用正则在整个文件上按行文本搜 `horizon: R(...)`，
它**只匹配文档里第一处**，于是三套预设都被改成第一套的坐标，
MAP_FIRST 与 INFO_FIRST 立刻报 `('trend','horizon','overlap')`。
**正确做法是按预设名切成三个块、在每个块内部替换。**

### 卡片底色由各自的强调色混出来，不做统一底色

22 张卡如果共用一个底色，整屏读起来就是一片同色。但**也不能每张卡各自动手调色** ——
那就不是一套设计系统了。

做法是让**算法统一、结果分化**：`backgroundColor: color-mix(in srgb, <accent> 9%, <panel>)`。
讲预警的卡偏红（此刻态势 / 最近告警）、讲雨情的偏青（分时雨量 / 累计雨量）、
讲预测的偏紫（水位与预测 / 十站预测）、讲地图的偏蓝。浓度都是 9%，
所以饱和度一致、仍然是一套语言，但每块有自己的色彩身份。

为什么用 `color-mix` 而不是手算 `rgba` 叠加：它是浏览器原生混色，色相过渡准确；
手算 sRGB 叠加在低浓度下会发灰。大屏跑在 Chromium 上，支持度没问题。

### 「不够紧密」和「留有空隙」常常是同一个原因

底部四张小卡曾出现两种相反的症状：`站点排行` 下面空一条、`超阈时长` 的脚注被切半行。
根因是同一个：**内容高度按字号算，而容器高度由版面给，两边不对账**。

对症的修法不是调字号（调到刚好放下，换个数据又不对），而是**让内容分掉容器的剩余高度**：
给每一项 `flex: '1 1 0'`，由容器均分。这一条在 `站点排行`、`超阈时长`、
`多预见期预测`、`三因子研判` 上都用过 —— 凡是「N 行等分的列表」都适用。

另外要注意**副标题折行会撑高 header**：`站点排行` 的副标题「三个角度各取前三，回答「先管哪个」」
在 292px 宽的卡里折成两行，header 高一倍，body 从 78px 掉到 40px，
两列内容被 `overflow:hidden` 整块裁掉 —— 看起来像「卡片中间空着」。
副标题压成一行「各取前三 · 先管哪个」之后就好了。

### 阈值参考线要放在 DOM 层，不要放进会被拉伸的 SVG

大屏的图用 `preserveAspectRatio="none"` 让曲线铺满容器 —— 代价是所有 SVG 坐标
**按容器尺寸等比拉伸**。把阈值标签（红0.42 / 橙0.28…）放在 SVG 里，
卡片一改宽，标签就被推出右边缘切掉；把字号调大调小都只是碰运气。
挪到 SVG 外层的 DOM 绝对定位后，位置用百分比、字号由 CSS 决定，与拉伸彻底解耦。

### 数字能画的就别写出来

右侧 `超阈时长` 原本是一列数字，改成横向条形图：条形长度一眼能比「谁泡得久」，
数字要逐个读。轨道保留（能看出「还差多少到最长」），数值只作辅助。

### 大屏第二、三屏：辖区预测与全域研判

第二屏**不放地图**，整屏六格——五个街道各一格 + 一格全域合计。每格一张 12 小时
预测曲线，横轴时间、纵轴水深、四级阈值横带，峰值打点、达峰时刻写在标题行。
十站按辖区归并，每区 1~3 站每站一条线，最高等级那条画粗。

六格**共用一条纵轴**，否则「东城看着比西城高」只是刻度不同。但共用时要排除
「全域合计」那一格：它画的是十站相加（约 7 m），和单个辖区的积水深（0.5~1.5 m）
不是同一个量，算进去会把另外五格压成贴底边的直线。合计格自己按同一域绘制，
曲线超出上沿被裁掉是正常的——它本来就不该和外区比高度。

第三屏是**全域研判**，五张统领性分析 + 一条数据质量窄带：

| 面板 | 回答什么 |
|---|---|
| 全域水位演进热力图 | 这波是怎么蔓延开的、哪些站同步上涨 |
| 风险格局 | 又深又涨 / 深但转退 / 浅但在涨 / 平稳，先救谁 |
| 全域趋势研判 | 这一波是收尾还是要来第二波 |
| 预测可信度 | 哪几个站的预测敢信 |
| 多区对比 | 五个区谁排第一 |

#### 三条纪律

**一、过去那一半必须是真实历史。** 热力图最早的版本用「当前等级」平铺过去六格，
图形看着是满的、实际零信息——它让读者以为过去六小时一直这样，而其实什么都没测。
现在走批量接口 `/api/history?hours=12` 一次取回十站历史（逐站请求是十次往返，
24 秒轮一轮播就重拉一遍）。

**二、没数据就说没数据。** 取不到历史的那一格是 `'blank'`（一条空心虚线框），
不是 `'none'`（实心正常灰）。两者都用同一个灰的话，读者会把「缺数据」读成
「情况良好」——这是最危险的一种误读。`'blank'` 特意不放进 `Level` 领域类型：
「有没有测到」不是水位等级。

**三、退水时「峰值」这个词会骗人。** 预测曲线只有未来、没有历史，退水时窗口内
最高点必然就是起点。写「12h 峰值 0.53 m」会让人以为之后还能涨到 0.53，实际含义
是反的：此刻已是这一段最高。所以峰在起点时改口径——标题写「此后最高 · 就是此刻」，
底注把「峰值在」换成「最深在」。

### 画布适配：宁可两侧留边，也不裁掉一格内容

大屏是 1920×1080 的固定画布，靠 `transform: scale()` 适配实际屏幕。踩过一轮，
记录在这里：

**症状**：同事在 1410×628（宽高比 2.245）的窗口里打开，说「整个页面上就显示了一点」。

**两次误修**

1. **先用 `Math.min`（contain）**——保证不裁，但 2.245 的窗口下 `scale = 628/1080 = 0.581`，
   画布只渲染 1116px 宽，右侧空 294px。看上去就像"没铺满"。
2. **改成"宽度定 scale、画布高度随视口浮动"**——宽度确实铺满了，但把逻辑高度从 1080
   压到 855，`rects` 的 y/h 同比压缩了 21%，而**面板内部的 flex 内容并不会跟着缩小**，
   结果是底部整行面板被裁掉一半。这是更糟的错：数据看不见了。

**最终做法**：回到 contain 缩放（`Math.min`），但把外层从
`position: fixed; inset: 0; overflow: hidden` 改成**居中布局 + 外圈同色底**。
- 内容一格不少（16:9 的版面在任何比例下都完整）；
- 画布居中，外圈用版面底色的最浅一档，读起来是「版面外缘」而不是「没渲染」；
- 不再用 `inset: 0 + overflow: hidden` 钉死外层——那会把超出视口高度的部分
  直接剪掉（1410×628 下 1080 逻辑高会变成 793px，比视口高 165px）。

**一句话**：宽高比不匹配是物理事实，`contain` + 居中 + 同色外圈是唯一
「不裁内容、不压变形、不显得没铺满」的解法。**不要为了填满去压缩版面高度——
面板内容不会跟着缩，只会被裁。**

### 大屏不是一屏铺满，是三轮播一遍

> 这一段讲的是 `/board/legacy`（旧三屏版）。值班台把它当常驻背景，
> 它要在一屏里同时摆出「全城 + 辖区 + 平台」三类信息，所以按屏轮播。
> `/board`（九页版）走的是另一条路：一页只回答一个问题，见上文「九页」。

旧三屏按**三屏轮播**组织，每屏回答一类问题。改之前是五屏、
每屏 6 块大面板平分版面——覆盖率有 96%，但只有一层，读者不知道该先看哪。
现在每屏都按「KPI 条 → 主图 → 明细」三层排，信息有主次。

| 屏 | 停留 | 块数 | 回答什么 |
|---|---|---|---|
| 全域总览 | 24s | 11 | 现在全城什么状态、最紧张在哪、出警了没有 |
| 地图分区 | 22s | 6 | 每个辖区此刻多深、12h 会不会更高、还在不在下雨、先看哪个站 |
| 平台运行 | 22s | 7 | 这套系统今天转得怎么样：数还准吗、人响应快吗、通知送到了吗、谁在动配置 |

**第三屏为什么不讲水位。** 前两屏已经把「城里现在怎么样、模型准不准」讲透了，
再放残差散点或精度矩阵只是重复。第三屏换成**运行记录**——数据新鲜度、告警响应时延、
通知投递成功率、审计流水、模型版本轨迹、告警趋势、累计雨量。这些平时散在管理页里
只有出事才被翻，放到大屏上是「平台真的在用」的证据。

**辖区看板取代了原来的辖区统计表。** 原来是一列列数字，要「读」；
现在改成「每区一行 × 四列」，四个列是四个不同的问题而不是四个字段：
现状（多深/什么等级）、12h 预测峰值（会不会更高/什么时候）、雨情（还在不在下）、
最紧张（该先看哪个站）。等级色只用在每行左侧那条竖条上，其余数字全用中性色——
一屏里彩色太多等于没有颜色可用。列宽用 fr 均分，所以辖区是 4 个还是 6 个都对齐。

三屏坐标不是手填的：用约束求解算出来再校验（不重叠、落在版面带内、
覆盖率 ≥95.9%），改版面时改参数不改数字。

**平台运行屏的五个新面板**（每块回答一个运维问题）：
- 数据质量监测：三段占比条（新鲜 <2min / 滞后 2~15min / 断连 >15min）+ 十站格阵，
  格阵颜色＝上报延迟。大屏最容易骗人的地方是引擎挂了两小时画面还在显示旧数据，
  这块把「多久没更新」直接摆出来。
- 告警响应时延：确认中位时延、处置中位时延、已接手占比三个 KPI，
  加一张「<1min / 1~5min / 5~30min / >30min」分档直方图。响了一小时没人理，
  再准的模型也没意义；瓶颈通常只在其中一段。
- 通知投递：按渠道拆成功与失败。「发了但没送到」是最难发现的一类故障——
  后端日志是 200，接收方什么都没收到。
- 操作审计：近 24h 写操作、参与人数、失败数。一张只读的大屏如果没人操作过，
  说明它其实没被纳入流程。
- 模型版本轨迹：历次版本的 3h skill 折线。换版如果 skill 没上去，那只是版本号变了。

**辖区看板的聚合口径**（写在领域注释里，别改）：积水深按**最深**取、变幅按**均值**取、
排序按「等级优先、同级比深度」。一个涵洞淹了就是淹了，平均会被旁边没淹的站摊平，
读起来像没事。

**编排上的两条纪律**
- **组件不随场景卸载，只淡出。** 卸载会让 SVG 图表重算、地图重新取瓦片，切屏时出现一片空白。代价是：不在当前场景的面板仍留在 DOM 里，量版面的脚本必须跳过不可见块，否则会报假溢出。
- **内容按实际分配高度自适应，不按场景名写死。** 「此刻态势」有四层内容（实测需 142px），地图屏只给它 132px；判断依据是面板矩形高度而非「它是地图屏」，这样用户在布局模式里拖高之后内容会自己长回来。

### 每个面板必须回答一个业务问题，答不上就重做

评审指出「多地方面板信息价值太低」。这一轮不是加装饰，是把**表达方式**换成能读的：

| 面板 | 改前 | 改后 |
|---|---|---|
| 多预见期预测 | 四行「水位 + 变化 + ±σ」，绝对水位读不出危险程度 | 加表头；每行加 **四级阈值色带**，并在色带上标出该预见期的落点；直接写「距红阈 已超 0.12m」；底部补 模型 / 修正量 / 增益 |
| 三因子研判 | 三条进度条 + 一个 0.00，读者不知道分数怎么来的 | 每条因子给出 **权重 × 原始值 × 折算分**（45%×1.00=45 分…），顶部一条权重堆叠条，底部给研判原话与分级门槛 0.22/0.40/0.60/0.78 |
| 近 24h 告警密度 | 12 根柱子，无刻度无数值 | 峰值柱标数、当前小时高亮、底部给「24h 共 N 次 / 峰值 M 次·x 小时前 / 本小时 K（环比 ±d）」 |

配色不再是清一色白：**每个面板的强调色都来自它自己的数据**——
此刻态势用当前最高等级色、预警构成用主色、告警类用橙/红、水位预测用紫色、雨情用青蓝。
卡面顶部掺该色 6% 的极淡底，标题前是同色竖条，右上角是同色框角。颜色是索引，不是装饰。

布局同时收紧：面板内边距 15→12px，栏间距 8→6px，两侧各加宽 6~8px（数字列不再挤）。

### 层次靠三级阴影 + 眉标，不靠加颜色

视觉升级没有再加一个颜色，只做了三件事（依据 ui-ux-pro-max 的 `dimensional-layering`）：

| 手法 | 具体做法 | 为什么 |
|---|---|---|
| 四级浮起 | `PALETTE.elev[0..3]`，1=贴地 2=常规卡 3=悬停/焦点 4=浮层 | 阴影全部带 `-12~-18px` 的**负扩散**，近处硬、远处散；均匀模糊会让白卡「浮」不起来 |
| 眉标（eyebrow） | `BigStat` 的标签 11px / 字距 1.6 / `textDim`，数字 54px 独占重量 | 原来标签与数字同色同重，读者要读一遍才知道哪个是值 |
| 微动效 | 面板入场 `bpRise`（位移 + 微缩）、数值变化 `CountUp` 缓动、外圈 60 道刻度 | 只让「刚更新的东西」动；满屏闪烁等于没有信号 |

主应用同步：`tokens.css` 新增 `--elev-1..4`，`.card-hover` 悬停抬到 `--elev-3`（只在 `@media (hover:hover)` 生效）。

### 版面是可调的，不是写死的

十一个部件各自带坐标，`web/src/board/layout.ts` 里保存三套预设：

| 预设 | 两侧宽度 | 用途 |
| --- | --- | --- |
| 均衡 | 286 / 322 | 默认，地图与数据各占一半 |
| 地图优先 | 250 / 250 | 领导来看「淹哪儿」，把中间整块留给底图 |
| 信息优先 | 360 / 360 | 交接班看数，地图退成背景 |

点右上角**调整布局**后，每个部件顶部出现拖拽条、右下角出现缩放手柄，拖完点**完成**即写入
`localStorage`（键 `wl-board-layout-v2`），刷新与重启都保留。改动过的版面 `preset` 记作
`custom`，点**复位**回到均衡。

坐标一律夹在画布内（`clampRect`）：拖到屏幕外的部件等于丢失，这类编辑器最常犯的错就是这个。

### 地图跟着观测点平移

轮换到某个站时，底图中心平滑移到该站经纬度，站名落在视口正中，并画一圈虚线准心。

不出现空白的关键在于**双层交叉**：新中心的瓦片整层加载完成后才淡入，旧层在它下面继续显示，
等新层完全盖住再撤。任何一帧都有完整底图，不会闪白。

缩放固定 **z13**：黄岩十站南北跨 0.074°，z14 时约 980 像素——一旦中心落在最北的站，
南边的站就被推出画布；z13 时跨度约 490 像素，无论中心在哪一站十站都在视野内。


`/board` 是给**大厅常驻屏**用的一页：无交互、1920×1080 定尺、一屏装下全部部件，
只有「观测点」每 9 秒换一个。早先做过「四屏轮换」，那等于把四个页面重排一遍——
每次切走观众就得重新找自己在看什么。轮换的目的本来是让十个站点都有露脸机会，
不是让信息分时出现，所以改成**超集屏 + 单维轮换**。

视觉走**电视天气预报的演播室**那一套，层次是三层：

1. **最底**：演播室背景——深青蓝渐变 + 顶部光斑 + 球体弧线（大气层边缘）。
2. **中间**：**倾斜的城市地图平面**，`perspective(1900px) rotateX(38deg) rotateZ(-5deg)`，像一块斜放在演播室里的沙盘。它铺满整屏、四周内阴影压边，读作「一块浮着的屏幕」而不是「一张壁纸」。
3. **最上**：**实心白卡 + 双层投影**（近处一圈贴边影 + 远处一大片柔影）浮在两侧与底部。

**为什么最后没有用毛玻璃**：地图平面纹理很密（街坊格、支路、水系），`backdrop-filter` 糊完之后只剩一片奶白，
面板与地面的分界反而消失，层次塌成两层。实心白卡靠投影离地，边界清楚，3 米外也能一眼分出「这是读数，那是城市」。

地图之所以必须是背景而不是面板内容：面板有边框和留白，一旦把地图装进去，透视感立刻退化成「页面里嵌了一张图片」。
背景地图用 `preserveAspectRatio="slice"` 铺满、`rotateX(38deg)` 让近处大远处小；
**选 38° 而不是 45°**：45° 时纵轴余弦只有 0.71，街区被压成横条，看起来像拉伸的截图而不是俯视。
标记半径缩到 0.34 倍、字号缩到 7.4px——倾斜 + 铺满后整体放大约 1.9 倍，不缩就是一团团红球。

地名取 **台州市黄岩区**：十个监测站分别是天长北路下穿隧道、东城立交桥下、九峰公园西低洼段、
永宁江滨江泵站、新前模具小镇北闸、桥上街老巷口、台州站站前广场、西城快速路涵洞、
黄岩体育馆周边、南城永丰河排水渠（经纬度落在 121.20–121.28E / 28.60–28.69N 的真实范围内）。

版面按「从远处能读到什么」排序：

| 栏位 | 回答的问题 | 部件 |
| --- | --- | --- |
| 左 | 此刻有多严重 | 十站汇总 KPI、预警构成环、近 24h 告警密度、最近告警列表 |
| 中 | 在哪里、怎么走到这里 | **全城地图（铺满整屏做背景，当前观测点带呼吸环）**、轮换站水位+预测曲线、多预见期表、三因子研判+综合分环 |
| 右 | 这个站是谁、接下来会怎样 | 观测点头卡（含静态参数）、多类别对比、十站 12 小时预测、智能体决策 |

| 参数 | 作用 |
| --- | --- |
| `?scene=0` | 已废弃（超集屏不再分屏），保留兼容旧书签 |

主题已统一为浅色玻璃一套（原先的 `?theme=dark` 分支已下线）。

几条刻意的设计决定：

- **地图铺满整屏当背景，面板浮在上面**。参考「大厅大屏」的常见范式：中间是城市本体，四周是读数面板。地图一旦被装进面板，就只剩「一张图」而不是「这座城」。
- **地图是一块倾斜的平面，不是一个平面图层**。`rotateX(38deg)` 让近处街区大、远处小，观众读到的是「俯视一座城」而不是「看一张俯视图」；平面四周压内阴影，边界像投影幕。
- **面板用实心白卡，不用半透明**。理由写在 `web/src/board/parts.tsx` 的 `Panel` 注释里：地图纹理密，毛玻璃糊完只剩奶白，层次反而塌了。
- **大屏不共用主应用的配色令牌**。主应用是白底，告警色为过 AA 全压成了 ink 深色（如 `#B45309`）；大屏是 3 米外远看，需要高饱和。两边共用一套，两边都不合适。
- **轮换＝不同监测地点之间的数据轮换，且各部件协同更新**：换站时头卡、趋势图、多预见期表、三因子、地图高亮环同时淡入（同一个 `key` + `crossFade` 动画），观众看到的是「这一站被点亮了」，而不是五个面板各跳各的。地图、构成、对比、十站预测始终是全城的——它们是背景，不跟着轮换走。
- **中栏底部按 720×330 的画布反推成 655×300**：趋势图有自己的宽高比，给一个更宽的框只会左右留出两条空白，看起来像没画满。
- **同屏之内不混两代快照**：三因子与多预见期表都取自同一份 forecast；深度、雨强取实时遥测。混用 overview（30s 刷）与 forecast（60s 刷）会出现「峰值 1.5m 却显示正常」这种自相矛盾。
- **静态参数并入观测点头卡**，不单占一个面板——汇水面积、管网能力是「这个站是谁」的一部分，单独摆一块面板只会挤掉真正会变的东西。
- **告警密度条按时间正序画**（左旧右新）。先前的版本 index 0 是最新一格画在最左边，读起来是时间倒流。
- **「涨速最快」按当前趋势自动换口径**：全城都在退水时它恒等于 `+0.00`，没有信息量，此时改显示「回落最快」并按最负排序。
- **不做每帧 setState 推进度条**：轮换用 `setInterval`，动效交给 CSS keyframes。1920×1080 整树 60fps 重渲染在大屏盒子上很贵。

### 视觉语言只有一套

大屏最初的问题是：**地图是插画，面板是界面**。地图用绿坡、蓝河、金色虚线铺满，白卡却是克制的小字排版——两种语言并置，看起来像把地图壁纸贴在了仪表盘后面。

现在的做法是「**地图降级为底图，颜色只留给数据**」：

| 图层 | 处理 | 理由 |
| --- | --- | --- |
| 地块 | `#F7FAFD → #FCFDFF → #F2F7FB` 近白渐变 | 和白卡同一块白，不再抢注意力 |
| 街坊肌理 | `#F7FAFD` 实心 + `#E7EEF6` 0.7px 描边 | 只用线区分街区，不用色 |
| 山体 | 等高线式淡灰蓝 `#E8F0F8 → #F3F8FC` | 地形是背景信息，不该是插画 |
| 绿地 | `#EAF1E9` 0.7 透明度 | 几乎退到中性，只留「这里有块空地」的信息 |
| 水系 | `#D7E9F8 → #C2DBF0` + 白色 5px 高光 | 比原来降了两档饱和 |
| 主干道 | 白色 9px + **界面强调色** `p.accent` 0.26 虚线 | 原来的金色虚线是「装饰地图」的语言 |
| 建筑组团 | `#E1E9F2` | 中性灰，不与告警色争 |
| 站点气泡 | 半径系数 **0.2**、站名 6.2px | 倾斜铺满后整体放大 ~1.9 倍，气泡是「标记」不是数据图形 |

**底图是真实地图，不是示意图。** 用高德浅色路网瓦片（`style=8`）按墨卡托自己铺，
20 行投影代码，没引 MapLibre/Leaflet（大屏无交互，用不上那 200KB）。瓦片统一走
`saturate(0.22) brightness(1.04) contrast(0.94)` 降饱和——真实地图自带绿地、水系、POI 图标，
原样铺上来会和预警色抢注意力，而这一页的规则是「颜色只留给数据」。

**面板是半透明的，但不是毛玻璃。** 底色 `rgba(255,255,255,0.72)` + 一圈 `rgba(255,255,255,0.72)` 亮描边 + 顶部一道 `inset 0 1px 0` 高光，**没有 `backdrop-filter`**——毛玻璃会把底图的街道和水系糊成一片奶白，卡片与地面的边界消失，层次反而塌成两层；半透明则让底图纹理原样透上来一部分，读作「浮在桌面上的小组件」。

配套的一个前条件是**底图必须比卡片暗一档**：平面底色因此从近白 `#FBFDFF` 压到浅蓝灰 `#DCE9F5`。白卡叠白底只会看起来脏，不会通透——这是这一版唯一一处「为了透明度改底图」的调整。

**地图平面自己也是一块屏**：`borderRadius 20` + 1px 白色 30% 描边 + `0 40px 80px` 投影 + `inset 0 0 120px` 压边，和白卡同一套圆角/描边/投影语言。之前它是个裸 `div`，所以视觉上就是「贴了张地图壁纸」。

配套的三处收紧：① 面板正文统一 `overflow:hidden`（此前右栏「智能体决策」的 signals 网格、左栏「最近告警」都漏到卡片外，白底之外的深色演播室上小字几乎读不出）；② 白卡标题 17px→14.5px + 下沿 1px 发丝线，去掉左上角两根「半截断线」装饰；③ `Row` 标签降到 10.5px/`textFaint`、数值 `textDim`、每行 1px 发丝分隔，形成表格般的对齐节奏。

## 界面

**整个系统只有一屏。** 不是把十个页面塞进一个页面，而是把「十个页面各自回答的问题」
重新组织成**一屏里的层次**：左边是对象，中间是选中的那个对象的当前舞台，右边是
「你怎么走到这里的」以及这一路每一层的细节。没有标签栏，没有侧边导航，换对象不换页。

| 路由 | 是什么 |
|---|---|
| `/login` | 登录 |
| `/` | 工作台（全部业务能力都在这一屏里） |
| `/board` | 大厅大屏：无交互轮换，投到墙上用 |

旧的多页入口（`/sites`、`/alerts`、`/shift`、`/model`、`/rules`、`/system`、`/admin`、`/live`）
连同侧栏 `components/Layout.tsx` 一起删掉了。留着它们等于留着一条「没有导航、却能被地址栏打开」
的第二套界面，两套界面的口径迟早会分叉。旧链接进来一律落到 `/`，工作台自己从 URL 复原画面。

### 四个区，各回答一个问题

```
┌─ 事实条 ───────────────────────────────────────────────────────┐
│ 涝 现在最严重的是…   待办 5 项 · 激活中 5 条 · 模型 在线 · 链路●  │  ← 屏幕上写着的事实，每块都是入口
├──────────┬──────────────────────────────────┬─────────────────┤
│ 左栏     │ 中舞台                            │ 右栏钻取栈       │
│ 对象列表 │ 选中的那个对象，展成它该有的样子    │ 怎么走到这里的 +  │
│ 236px    │                                  │ 这一路的细节 452px│
└──────────┴──────────────────────────────────┴─────────────────┘
```

- **事实条**：现在多严重、还剩几件没完、在用什么模型、链路通不通。这四块不是装饰，
  是**入口**——点「待办 5 项」进值班交接，点「模型 在线」进可信度，点链路灯进四层链路。
- **左栏**：整屏唯一一份站点列表，**刻意不跟随舞台变化**。换舞台、换排序、点进任意一层，
  它都不重置——因为「我刚才看到的第三行」是人在这一屏里唯一的空间记忆。
- **中舞台**：九种，由左栏和事实条选择。它只画这一个对象该看的东西。
- **右栏**：钻取栈。点一个站、点一条预警、点一个指标，都会往栈里压一层；
  按 Esc 退一层，退空了才回到「态势」。栈**记的是路径**，不是历史——换舞台时清空，
  因为「在另一个舞台上怎么钻过来的」不是一条路径。

### 九个舞台

| 舞台 | 谁把它叫出来 | 回答什么问题 |
|---|---|---|
| 全域态势 | 默认 | 现在最严重的是哪一级、哪个片区、往哪走 |
| 站点舞台 | 点左栏任一站 / 地图气泡 | 这一站现在多严重、四档预见期、凭什么这样判、谁在管 |
| 预警卷宗 | 点左栏预警页签任一条 | 这条预警的两条轴各走到哪、下一步只有哪几个动作 |
| 值班交接 | 事实条「待办」 | 这一班还剩什么没完、SLA 还差几分钟 |
| 模型可信度 | 事实条「模型」 | 凭什么信它：离线指标、在线滚动、四族对比、版本治理 |
| 规则预演 | 可信度里的「判据是什么」 | 改成什么样会变成什么结果（**改之前先预演**） |
| 链路与接口 | 事实条链路灯 | 四层哪一层断了、断在那一层时屏幕上先出现什么 |
| 治理 | 事实条「治理」 | 谁能登录、谁改了什么、告警推到哪去 |
| 大屏 | 事实条「大屏」 | 投到大厅墙上的那一版（无交互，按 Esc 退出） |

### 状态只有一处：`workbench/model.ts`

```ts
type Stage = 'situation' | 'site' | 'event' | 'handoff' | 'trust'
           | 'rules' | 'plumbing' | 'governance' | 'wall'
type Crumb = { kind: 'site' | 'event' | 'metric' | 'layer' | 'api', ... }
interface WorkbenchState { stage: Stage; trail: Crumb[]; query: string; sort: RailSort; alarmsOnly: boolean }
```

用 `useReducer` 的八个动作（`stage / push / popTo / pop / pick / query / sort / alarmsOnly / home`）
表达全部交互，**没有第二个状态容器**。三条不显然的约定：

- **换舞台清空栈**，横向换站保留栈（`pick` 动作）。原设计是 `goStage` + `openSite` 两步，
  结果 `goStage` 的「清空栈」先执行，**挨个看十站时永远回不到上一个**——而看到第七个想退回第五个，
  正是最需要回退的那一刻。
- 同一个对象不重复入栈，已在栈里则**截断到它**（不是再压一层）。
- 筛选（`query` / `sort` / `alarmsOnly`）跨舞台保留：`home` 也不清它们。

地址栏是这一屏的第二个入口，也是分享用的：`/?on=site&site=S08&trail=s%3AS08&sort=rain`。
用 `history.replaceState` 而不是 `pushState`——否则「钻取」和「页面导航」混成一件事，
按一次后退只退掉「刚才点了哪个站」，而用户以为会退到上一个页面。

### 交互层：同一件事只实现一次

这一层是本项目的产品主张——**不是「把数据画出来」，是「让人能把事情办完」**。

| 文件 | 作用 | 一条不容易想到的约束 |
|---|---|---|
| `map/RealMap.tsx` | Leaflet 真地图：可拖、可缩放、点气泡飞行定位 | 站点是 WGS84、高德瓦片是 GCJ-02，**不纠偏偏 100~600 米**，所以 `map/geo.ts` 做 `wgs84ToGcj02`（逆变换迭代 3 次逼近） |
| `workbench/Drill.tsx` | 右栏钻取栈：只展开栈顶 + 轨迹条 + 「从哪开始」兜底 | 它替代了上一版的抽屉：抽屉一次只能表达一层，而「站点 → 那条预警 → 那次通知投递」是三层 |
| `workbench/Rail.tsx` | 左栏：搜索 `/` 聚焦、四种排序、只看预警、骨架屏、空态 | **不跟随舞台变化**，否则每点一次站，排序与滚动位置就重置一次 |
| `workbench/stages/*.tsx` | 九个舞台，各自只画一个对象 | 舞台之间不许互相 import；共享的东西下沉到 `kit.tsx`（排版）与 `visual.ts`（视觉） |
| `interactive/Tour.tsx` + `TourHost.tsx` | 九步演示流程，锚点用 `data-tour`，可替用户点一下 | 锚点**不用 CSS 选择器**：这个项目三次栽在「按第几个/什么形状找元素」上。目标缺失时流程不中断，卡片居中并说明「控件还没出现」 |
| `interactive/Tooltip.tsx` | 术语气泡 `Glossary` | 不用 `title` 属性：放不了结构化内容、延迟由 OS 决定（1~2 秒）读不出因果、且无法被测试 |
| `interactive/Toast.tsx` | 操作反馈，错误态 5.2 秒且**保留后端原话** | 409「不能从「已处置」直接改为「误报归档」」是给人看的，不能吞成「操作失败」 |
| `primitives/Rich.tsx` | `Emph` 只认 `**加粗**` 一种标记 | 刻意不做 markdown 渲染器——支持得越多，就越会有人往里塞表格和链接，最后界面变成文档 |

**可点性靠可发现性**：所有可点元素都带稳定标记（`data-rail-row` / `data-event-row` /
`data-fact` / `data-tour` / `data-sec` / `data-trust-link` / `data-sort`），
走查脚本按语义定位，不按坐标、不按「第几个」。工作台 32 项交互断言、九步演示流程、
十个检查面的裸星号扫描都有真点击的验收脚本在跑（见「验收」）。

### 前端五层，页面只做布局

```
pages/        只剩 LoginPage；业务页已经不在了
workbench/    这一屏：model（状态）、useWorkbench（接线）、FactBar / Rail / Drill、stages/ 九舞台、kit / visual
view/         视图模型：把领域数据组织成「舞台要的那个形状」
components/   primitives（无领域知识）/ domain / charts / interactive
data/         DTO + adapter（唯一换算点）+ client + queries + SSE 单例
domain/       15 个纯模块：品牌类型、时间、等级、研判、规则、指标、鉴权…
```

为什么要分这么细：一个文件里同时做取数、派生、布局、展示，就有四个互不相干的修改理由；
而「水位」和「积水深」都是 `number`，混用已经造成过两次真实 bug（引擎把增量当绝对水位，
误差 +7.85m；前端把 10 站水深相加显示 3.21m）。领域层用品牌类型（`Meters` / `Depth` / `Delta` / `Rate`）
把这些量分开，换算是 `data/adapters.ts` 的唯一职责。

几个刻意的设计决定：

- **事实先于导航**：入口是屏幕上已经写着的事实（「激活中 5 条」「模型 在线」「链路●」），
  不是菜单。人想问什么，屏幕上就写着什么，点它。
- **结论先于证据**：态势舞台左下角是「当前最严重」的一句话，然后才是地图、分布、走向。
- **刻度是通用语言**：积水深度、综合分、持续时长都用带阈值的 `Ruler`，
  「还差多少到红」比「现在是 0.42m」更直观。
- **不只用颜色编码**：变化量同时给箭头和数值，色盲与黑白打印都能读。
- **可信度是独立维度**：数据滞后、传感器劣化、SSE 断连三种情况在事实条上直接标出来，
  而不是让这一屏看起来一切正常。
- **两个 hook 的数据不是同一时刻的同一对象**：这个项目三次栽在这上面
  （降雨-积水响应图曾经「曲线是 A 站的、阈值是 B 站的」，因为基准高程取自 `/api/sites`
  而曲线取自 `/api/sites/{id}/history`）。规矩是：同一块图上的所有量必须来自同一次查询的同一个对象。
- **动画尊重系统设置**：`prefers-reduced-motion` 下全部关闭（大屏轮换整个不启动，不是只关 transition）。

## 账号与角色

首次启动自动创建 `admin`（口令取 `WL_BOOTSTRAP_ADMIN_PASSWORD`，默认 `admin123`），
启动日志会打印一次，登录后应立即改掉。

| 角色 | 能做什么 | 典型是谁 |
|---|---|---|
| `admin` 系统管理员 | 改研判规则、切换模型版本、触发重训、管账号、看审计、配推送 | 系统负责人，一个月动两次 |
| `operator` 值班员 | 确认预警、派单、推进处置、写备注、改规则前预演、触发降雨注入 | 值班室，一直在点 |
| `viewer` 只读 | 只看，不能写 | 领导、外部门、只读投屏 |

几条刻意的约束：

- **能力表在领域层**（`web/src/domain/auth.ts` 的 `MIN_ROLE` 与 `can()`），
  和后端 `RequireRole` 用同一套判断。界面按钮亮不亮与接口通不通必须是同一个答案，
  各写一遍的结果就是「界面上能点、点了 403」。
- **不能把最后一个可用管理员降级或停用**，否则没人能再进系统。接口返回 409。
- **改口令或停用会立刻作废该账号全部会话**——口令改了但旧 cookie 还能用，等于没改。
- **不能停用自己、不能降低自己的角色**（防手滑把自己锁在门外）。
- 会话是**不透明随机令牌 + 库里只存 SHA-256 摘要**，不是签名 cookie；
  库泄露时摘要不能当 cookie 用。有效期走墙钟（`WL_SESSION_TTL_H`，默认 12h），
  不跟 60x 仿真时钟。
- 登录时账号不存在也会跑一次假 PBKDF2，把响应时间拉平——否则快/慢就是用户名枚举通道。

## 操作审计与推送

**审计**只记写操作（`POST`/`PUT`/`PATCH`/`DELETE`，排除引擎推数据的 `/api/ingest/`）。
读接口也记的话，一天几千条里要查的那条会被埋掉。每条含操作人、角色、方法、路径、
状态码、耗时、来源 IP、request id 和一句人话摘要（「修改研判规则」「确认预警」「派单预警」）。
被拒绝的请求（401/403/409）同样留痕——「谁试过改规则但被拦住了」是有价值的信息。

**推送**两个渠道：

- `inapp` 站内弹窗（SSE 广播），**不可关闭**——它是最后的兜底。
- `webhook` 外部地址，默认关闭，需配 endpoint 才能启用；可设最低推送等级与去抖分钟。
  请求体 `{"text","site_id","site_name","level","action","peak_value","duration_min","reason"}`，
  签名密钥走 `X-Waterlog-Secret` 头。

只在 `raised` / `upgraded` 时推送。每轮预测都推（`updated`）会变成骚扰，
值班员三天就会把通知静音，那时真的红色预警也进不来。**推送不重试**：
预警要的是及时，不是最终一致。

## 验收

```powershell
.\scripts\acceptance.ps1                  # 完整验收（含降雨注入与状态机全链路，约 12 分钟）
.\scripts\acceptance.ps1 -SkipStorm       # 只验接口契约与数据自洽性（约 40 秒）
.\scripts\acceptance.ps1 -Shots           # 顺带重截工作台八张动作图，并跑三套真点击走查
.\scripts\acceptance.ps1 -User x -Password y   # 换验收用的账号
```

当前基线：**PASS 63 / FAIL 0**（`logs/acceptance-20261115-041124.tsv`）。

脚本逐条打印「期望 vs 实际」，最后汇总 PASS/FAIL 并把明细写入 `logs/acceptance-*.tsv`，
退出码 0 表示全通过。它检查的不是「接口返回 200」，而是这些**能证伪**的东西：

- 置信区间是否真的包住点预测、预测水位是否在物理约束内；
- 融合模型是否真的全面优于持久化基线、90% 区间 PICP 是否在 88~98%；
- 线性外推是否真的劣于基线（这是「预测有价值」的反证）；
- 在线 skill 是否被高程差虚抬（口径自洽性）；
- 暴雨注入后预警等级是否逐级升到红色、四态机两条迁移路径是否都走通；
- 重复确认是否真的返回 409 而不是静默成功；
- 处置轴是否真的拦住非法迁移（已派单不能退回待处置）、同态重复是否被拒；
- 规则 PUT 是否即时生效；
- **未登录是否真的进不来**（401），**只读账号改规则是否真的被拒**（403）——
  这两条最值得测：鉴权写错时接口照样返回 200，前端看起来一切正常；
- 审计是否记到了操作人（中间件顺序写错时会静默记成空字符串）。

前端的三套走查脚本。截图只证明「画出来了」，证明不了「点得动」，所以下面三件事都是真点击：

```powershell
node scripts\shoot-workbench.mjs --no-storm   # 32 项交互断言 + 八张动作图
node scripts\shoot-tour.mjs                  # 演示流程九步，逐步验锚点命中
node scripts\check-stars.mjs                 # 十个检查面找裸 markdown 星号
```

`shoot-workbench.mjs` 自带注雨：`POST /api/sim/storm` 后轮询 `/api/overview`，直到十站最深积水 ≥0.5m
（实测约 70 秒）。**注雨失败立刻抛错**——否则会空等 200 秒，把「注雨接口坏了」伪装成
「页面上没有数据行」，而后者看起来像组件坏了。加上 `--no-storm` 则用当场已有的数据复跑。

三个脚本覆盖的是三件不同的事：交互（点击有没有生效、状态有没有被重置）、
引导（九步锚点还在不在）、文案（有没有漏渲染的标记）。任一件都不能靠另一件代替。

### 为什么要有「排空积水」这种假接口

真实系统里没人能把积水排空，也没人能叫停天上的雨。
但这个模拟器的退水极慢——管网满负荷、堰流系数只有 0.03~0.05、还有漫溢拓宽，
一场 160mm/h 的雨能让水位在阈值上待十几个小时仿真时间。
没有 `reset-water`，验收四态闭环里的「条件消失 → 自动解除」就只能干等，
等不到就报 FAIL，而真正坏掉的是测试设计而不是系统。

所以它是**验收通道专用**的：清零各站水深、把特征缓冲重写成「这座城市从没下过雨」、
并作废清零前发出的未结算预测（那些预测瞄准的是被抹掉的那条洪水曲线，
留着结算只会把在线 skill 抬成一个漂亮但假的数字）。
`dropped_pending` 字段会告诉你作废了多少条。

生产环境里这两个接口应该整段删掉——它们和真实业务无关。

## 预警四态

```
ACTIVE_UNACK ──ack──► ACTIVE_ACK ──解除──► CLEARED_ACK
      └──────────────解除────────────────► CLEARED_UNACK
```

非法迁移（重复确认、确认已解除事件）返回 409 并说明原因，前端原话展示不吞错。

**处置状态是另一条轴**，与四态互不影响：

```
open ──► dispatched ──► onsite ──► resolved ──► open
  └──────────┴───────────┴──────► false_alarm ──► open
```

四态回答「预警还成立吗」，由模型决定；处置回答「我们做了什么」，由人决定。
一条已经 `CLEARED_ACK` 的预警，处置可能还停在 `dispatched`——人还没到现场，
雨已经停了。合成一个状态机就没法表达这件事。`dispatched` 不能退回 `open`：
已派单不能假装没发生。

## 已知边界

- **数据是模拟的**。算法链路是真的，数据源不是。接真实数据只需实现 `sim.py` 的
  `advance()` 同构接口（返回 `step/rain/level/quality/rain_fc_*`）。
- **60 倍加速**：5 分钟仿真步长对应 5 秒墙钟，所以 12 小时预见期在页面上约 12 分钟走完。
  这带来一个必须记住的坑：**所有时间窗口都要用仿真时钟，不能用 `time.time()`**，
  否则仿真时间跑到墙钟前面之后，窗口会算错一个数量级。
- **发布渠道只有站内弹窗 + 一个 webhook**，短信/大屏/电话未接。
- **鉴权是本机级**：HttpOnly 会话 cookie，`Secure` 故意没设（本机 http 设了浏览器不回传），
  上线必须挂 TLS 并打开。没有 OAuth/LDAP，没有口令复杂度与锁定策略。
- **容器化配置未在本机验证**：本机没装 Docker，`docker-compose.yml` 与两个 Dockerfile
  是按镜像构建逻辑写的，`make up` 这条路没有实测过；`start.ps1` 那条路是实测的。
- 前端 bundle 1.37MB / gzip 451KB（ECharts 占大头），未做代码分割。
- 模型是表格型梯度提升树，不是时序深度模型——60 天样本量下这样更稳，
  换成 LSTM 需要更长的历史才不糊。
- **站点之间没有水力联系**，不考虑上游来水，只有空间降雨差异。
- 模拟器参数是手工标定的「看起来对」，不是率定模型，不能用于真实工程决策。

算法链路的逐段推导、参数取值理由、以及踩过的坑（量纲混用、skill 口径、
验证集划分）都写在 [docs/01-算法链路说明.md](docs/01-算法链路说明.md)，
实测证据在 [docs/02-验收报告.md](docs/02-验收报告.md)。
